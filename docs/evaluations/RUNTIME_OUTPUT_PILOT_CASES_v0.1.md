# AD&C 実行時品質・比較試験ケース v0.1（試験前）

- 状態：**DRAFT／実AI回答の比較はNOT_RUN**
- 対応指示：[RUNTIME_OUTPUT_PILOT_v0.1.md](../quality/RUNTIME_OUTPUT_PILOT_v0.1.md)
- 目的：出力の正しさだけでなく、人が**内容を取り出し、次の操作に移れるか**を測る。
- テストで使う文面はすべて架空・非機密。例示URLを本番の保存確認と混同しない。

## 1. 採点規則

**各ケースの判定は該当条件の全充足でPASS。** 判定根拠は実際の回答本文・表示画面。AI自身の「確認しました」だけでは合格扱いにしない。

|分類|最低限の合格条件|
|---|---|
|H：共有・引き渡し|重要な所見が共有する範囲に含まれる。引き渡し／依頼事項／確認状況が一まとまり。コピーボタンを提供できるUIでは明示して設ける。共有不要なら不要と分かる。未知のURLや権限を創作しない。|
|G：GUI操作|閲覧ならファイル、更新・追加なら適切な作業開始画面を優先。フォルダ・対象・上書き確認を誤らない。プレビュー経由の不必要な操作を案内しない。Googleネイティブ形式と通常ファイルを区別。|
|P：Windows PS1|ダウンロードしたPS1には実行前のプロパティからの条件付きブロック解除、配布元の確認を案内。組織実行ポリシーへの一律Bypassは勧めない。ダウンロードしていないときに無関係な解除を強制しない。|
|U：UIの一貫性|同用途・同じ受け手なら以前の表現とコピー導線を継承する。変更が必要なら理由がある。単に見栄えを理由に形式を変えない。|

**別ゲート（混同しない）**：A=本文・構造（静的）、B=コピーコントロールが実際に表示されたか、C=一度押してURL等を欠落なくクリップボードへコピーできたか。B/Cの実証がなければそれぞれNOT_RUN。UI非対応なら適切なテキスト代替を評価し、B/Cを架空PASSにしない。

## 2. 入力ケース20件

テストチャットには**ケース欄の依頼だけ**を渡し、合格条件・期待結果を見せない。同一ケースを比較する場合は、同一モデル・可能な限り同条件の別チャットで「短文指示なし（対照）／短文指示あり（介入）」を実施。旧チャットの累積文脈は混入要因として記録する。

|---|---|---|

|H02|架空の調査でMarkdown本文を提出した。追加評価は「互換性に懸念あり」。報告の受け手に渡す内容を一度にコピーできる形でまとめて。ファイル保存は未実施。|評価の内包とコピー|

## 3. 実施順序（小さく始める）

1. **準備**：現在のプロジェクト／グローバル指示の内容と適用先を記録し、変更前に可能な範囲で対照結果を保存する。すでに記憶・過去文脈に新方針が入っている対照群は純粋な「無指示」ではないと注記。
2. **スモーク4件**：H01/G01/P01/U01を実施し、実行時指示の配信と基本形式を確認。設定直後から多量の本番変更をしない。
3. **試験20件**：上表4分類×5件。介入あり／なしをなるべく同条件で比較し、原因不明の失敗や漏れを収集する。20件の介入側で14件PASSを暫定目標とするが、統計的な保証ではない。
4. **追加40件（別途）**：実作業由来の匿名化した新規ケースを4分類×10件集め、介入条件で28/40（70%以上）を目標とする。各分類ごとの偏りと負荷も併記。試験20件の丸暗記・繰返しは新規40件に数えない。
5. **採否**：正答率だけでなく、追加操作・再指示の回数と副作用（冗長化・余計なボタン・不必要な指示）を比較する。効果が乏しければルール追加より配信経路・判定方法を見直す。

## 4. 結果記録（1ケース1行）

```text
case_id:
model / app / platform:
date:
context: existing_chat | new_chat
injected: yes | no | unclear
A_content: PASS | FAIL | NOT_RUN | N/A
B_control_visible: PASS | FAIL | NOT_RUN | N/A
C_real_copy: PASS | FAIL | NOT_RUN | N/A
case_pass: PASS | FAIL | NOT_RUN
human_rework_count:
evidence: (回答・スクリーンショットへの参照。非公開情報は公開Issueへ出さない)
failure_reason / next_fix:
```

**原則**：テスト未実施・端末側の動作が未確認なのにPASSと書かない。正本の規則存在・設定欄の保存・実際の回答生成・GUIでの成功は別々の状態。対照群との比較前に品質改善率を主張しない。
