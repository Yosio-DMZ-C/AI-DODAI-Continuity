# AD&C 実行時品質・比較試験ケース v0.1（試験前）

- 状態：**DRAFT／実AI回答の比較はNOT_RUN**
- 対応指示：[RUNTIME_OUTPUT_PILOT_v0.1.md](../quality/RUNTIME_OUTPUT_PILOT_v0.1.md)
- 目的：出力の正しさだけでなく、人が**内容を取り出し、次の操作に移れるか**を測る。

## 1. 採点規則

**各ケースの判定は該当条件の全充足でPASS。** 判定根拠は実際の回答本文・表示画面。AI自身の「確認しました」だけでは合格扱いにしない。

|分類|最低限の合格条件|
|---|---|
|H：共有・引き渡し|重要な所見が共有する範囲に含まれる。引き渡し／依頼事項／確認状況が一まとまり。コピーボタンを提供できるUIでは明示して設ける。共有不要なら不要と分かる。未知のURLや権限を創作しない。|
|G：GUI操作|閲覧ならファイル、更新・追加なら適切な作業開始画面を優先。フォルダ・対象・上書き確認を誤らない。プレビュー経由の不必要な操作を案内しない。Googleネイティブ形式と通常ファイルを区別。|
|P：Windows PS1|ダウンロードしたPS1には実行前のプロパティからの条件付きブロック解除、配布元の確認を案内。組織実行ポリシーへの一律Bypassは勧めない。ダウンロードしていないときに無関係な解除を強制しない。|
|U：UIの一貫性|同用途・同じ受け手なら以前の表現とコピー導線を継承する。変更が必要なら理由がある。単に見栄えを理由に形式を変えない。|

**別ゲート（混同しない）**：A=本文・構造（静的）、B=コピーコントロールが実際に表示されたか、C=一度押してURL等を欠落なくクリップボードへコピーできたか。B/Cの実証がなければそれぞれNOT_RUN。UI非対応なら適切なテキスト代替を評価し、B/Cを架空PASSにしない。

## 1.1 成功率の分母とA/B/Cの集計契約（2026-10-16追補）

**① 70%は「初回回答のA＝内容・構造の合格率」の試験目標。** 分母は事前に定めたケース数で固定し、介入（指示あり）の20件であれば **14/20以上**、後日に初めて投入する別の40件であれば **28/40以上**を暫定目標とする。対照（指示なし）も同じケース集合で測り、指示ありの率だけで改善を主張しない。重大な誤誘導・安全上不適切な回答は、単に合格件数を満たしても要レビューとする。

**② AのPASSは、回答本文に必須の情報・手順・適切なコピー手段（使える形式の提供）が含まれるかの評価。** 同じ回答でも、ボタンを出力したことと、利用者画面に表示されたことは区別する。Bは対応環境における**実レンダリング**、Cは**実クリックと貼り付け結果**だけで判定する。画面を確認していないB、操作していないCはNOT_RUN。環境が専用ボタンに非対応と確認でき、適切な代替テキストがある場合だけ、理由を記録してB/CをN/Aとする。対応UIで必要なボタンが表示されなければBはFAIL、未操作のCはNOT_RUNのまま。**AのPASSを実利用成功率に転用しない。**

**③ 未完了データの扱い**：1ケースを1単位とし、U類は同じケースの2回答を組にして初めて1判定。AがPASS／FAIL／NOT_RUNの件数を合計すると、各条件で常に予定の20件（スモークなら4件）になる。未入力・途中停止をFAILに繰り入れずNOT_RUNとして残す。ただしNOT_RUNを分母から隠して目標達成を宣言しない。中間報告では **PASS/予定件数、FAIL/予定件数、NOT_RUN/予定件数** を併記し、実施済みだけの参考率を出すなら必ず`PASS/(PASS+FAIL)`・対象数・未実施数を明示する。**全件のA判定が揃ったときに限り、正式な14/20・28/40の達否を判断する。**

**④ 操作性と副作用は別集計**：H01のB/C（及び対応プラットフォームのコピーUI）は表示・クリップボードの実測件数で報告。他ケースの外部Drive上書き・PS1実行などは試験範囲外であり成功と数えない。人間の再指示・操作探索・手戻り回数、冗長化・不要なUI、安全上の誤案内は個別に記録する。未測定なら数値を埋めずNOT_RUNとする。

## 3. 実施順序（小さく始める）

1. **準備（独立チャットを維持）**：プロジェクトへの一括移動や全体カスタム指示は行わない。通常の独立チャットでの自然発生の失敗を観察・記録し、機密を除去したケースを抽出。対照群と介入群のモデル・プラン・端末・旧チャット文脈を記録し、既存記憶を含む群は純粋な無指示とみなさない。
2. **スモーク4件**：H01/G01/P01/U01を個別の試験チャットで実施。介入側だけ短文指示を手動で貼り付ける。自然発生ケースの観測と、同条件比較の得点は混同しない。
3. **試験20件**：上表4分類×5件。介入あり／なしをなるべく同条件で比較し、原因不明の失敗や漏れを収集する。20件の介入側で14件PASSを暫定目標とするが、統計的な保証ではない。
4. **追加40件（別途）**：実作業由来の匿名化した新規ケースを4分類×10件集め、介入条件で28/40（70%以上）を目標とする。各分類ごとの偏りと負荷も併記。試験20件の丸暗記・繰返しは新規40件に数えない。
5. **採否**：正答率だけでなく、追加操作・再指示の回数と副作用（冗長化・余計なボタン・不必要な指示）を比較する。効果が乏しければルール追加より配信経路・判定方法を見直す。

### 実行条件・比較単位

- 同一モデル・プラン・端末・なるべく同じ会話条件で、**対照＝短文指示なし／介入＝[短文指示](../quality/RUNTIME_OUTPUT_PILOT_v0.1.md)を当該チャットへ一度だけ手動投入**を比較。共通標準や試験票・評価基準を受験AIへ見せない。既存の指示・Memory・過去文脈が混入したら記録し「完全な無指示」と称さない。

### 判定・停止と引継ぎ

- **A**は回答原文からPASS/FAIL/NOT_RUNを採点。**B**は実際の画面表示、**C**は実際のクリップボード内容を独立採点。B/Cの適用外は理由付きN/A、未操作はNOT_RUN。本文AのPASSだけで操作成功や総合成功を保証しない。
- **集計を2段に分ける**：①初回回答の内容・構造（対照／介入それぞれAのPASS/FAIL/NOT_RUNを予定4件を分母に併記し、比較成立の対数も別記）、②操作の検証状況（H01のB/C）を別記。実操作が必要なのに未確認なら総合実利用成功は**NOT_RUN**。Aだけの4/4を「操作を含めた4/4」と報告しない。
- **停止条件**：Foundationの進行と競合、新規チャット作成・人間の手操作をまとめて要請する必要がある、採点条件が曖昧、指示配送が確認不能、意図しない外部書込・公開・実行を求める状況。停止時は観測済み分と未実施分を分けて記録する。
- **リーダー報告**：`[RESULT ADNC-T005]` として、事実／仮説、重大な失敗、副作用、最大3件の最小改善案、A/B/CのPASS/FAIL/NOT_RUNと根拠、必要判断**1件**を統合Issue #13へ報告。キュー本文の状態確定はリーダーが行う。

## 3.3 追加実例：朝のリマインドの質問漏れ・通常表示の負荷（2026-10-18／改善候補・未採用）
