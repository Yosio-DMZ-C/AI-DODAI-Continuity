# AD&C 差分手順｜1.5.2 → 1.5.3

> **実行前品質ゲート：FROM=`1.5.2`、TO=`1.5.3`**。既存KBの`START_HERE.md`に導入版1.5.2が実在し、[UPDATE.md](UPDATE.md)で区間照合と差分表提示・今回の承認を満たした場合だけ適用。導入版不明の旧KBはこの数値更新をせず[ADOPT_LEGACY.md](ADOPT_LEGACY.md)で互換対応する。**互換プロトコル版1.5.2を導入版とみなさない**。

## 対象と保全

## 差分適用

1. `START_HERE`・`BUILD_PLAN`・`registry`、変更対象の本文とfileId、改訂番号、取得できるDrive version、現行SHAを取得。**旧版の現行実体を既存90_historyまたは既存のDrive履歴へ保全**。他担当の編集中・取得不明なら停止。
2. 現行の[PROJECT_EXECUTION_STANDARD.md](../PROJECT_EXECUTION_STANDARD.md)で「今回の本人指示 → 今回の案件で実取得した採用済み条件 → 未決定部分の一般標準 → AIの安全な裁量」という順序を確認する。**過去に使用しただけの素材は新たな採用条件・課金承認にならない**。
3. `START_HERE`へ上表の`ADNC_EXECUTION_STANDARD`を重複なしで追加。対象案件の採用条件と履歴の混在が存在する場合のみ、`BUILD_PLAN`の**その案件の現在欄だけ**へ短い区別を追加。履歴を削除しない。元に無い秘書・日記・Task機能は作らず`NOT_RUN`を保持。
4. **書込直前**に対象実体と関係するregistryの現行SHA等を再取得し、編集開始時から変わっていれば無断上書きせず対象だけ保留。これは競合の検出でありDriveのatomic CAS保証ではない。
5. 承認済みの対象を**元のfileId**へ差分保存し、今回の変更対象だけregistryのSHA/revisionを同期。変更後の原本・registryを再取得し、ID・変更前本文の保全・対象SHA・現在の採用位置が合致した時点で`ADNC_INSTALLER_VERSION: 1.5.3`を確定する。途中不整合ならその区間は未完了とし、他者変更を消さない。
6. 報告では「導入版の更新PASS」と「日次秘書／継続作業／コード実行の実動作PASS」を分離。独立AI・Google Drive競合排除・全件索引再生成は**別の実験**であり、この区間の完了だけではPASSにしない。

## 機能・試験範囲の明記

この版は一般標準より案件固有の実採用条件を優先する入口、対象限定の更新前後整合、構造検査への**任意**の導線、次回チャットへの引継ぎを整える軽微な更新です。既存KBへ本番の新しい排他サービスやスケジューラ、索引生成器を導入しません。サーバー側の原子性は依然**未保証**です。
