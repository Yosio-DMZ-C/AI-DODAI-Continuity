# AD&C 差分更新ガイド｜インストーラー 1.4.0 → 1.5.0

> **実行前品質ゲート：FROM=`1.4.0`、TO=`1.5.0`（インストーラー版、数値で厳密照合）**。現在の対象KBの実取得済み導入版が**ちょうど1.4.0**で、[UPDATE.md](UPDATE.md)の経路検査・差分表提示・本人承認が成立した場合のみ、この一区間を実行。違う版なら**適用禁止**。完了後のDrive読戻しとregistry整合PASSまで次の版へ進まない。
## 変更の目的
既存の「秘書日々の確認」（定期実行・手動呼出共通）へ、1日1回以下の**読取専用**バージョン確認を組み込む。新しいタスク／DB／監視サーバーは不要。個人KBの保存先は変えない。

| 対象 | 差分 | 保持するもの |
|---|---|---|
| `START_HERE.md` | `ADNC_INSTALLER_VERSION` を検収後 `1.5.0` に変更 | NodeID・Drive fileId・他の入口 |
| 既存の秘書日々の確認指示 | 下記の「日次バージョン確認」を末尾へ1段落追加 | 既存の予定／日記／質問／対話／優先度 |
| 既存の当日日記 | バージョン確認が実際に成立した日に短い状態コメントを追加 | 日記本文・出典・個人TASKS |
| `registry.json`等 | 変更済みファイルだけ必要な版/hash/size同期 | 他の登録と履歴 |

## 実行条件
1. 対象は利用者が指定した**現在のKBのみ**。`START_HERE.md`、`BUILD_PLAN.md`、`registry.json`、秘書の現行指示と保存先を取得し、既存の導入版が**1.4.0**であると確認する。不明ならNOT_RUNで停止し推測しない。
2. 差分表を示し、本人の**今回の既存KB変更への承認**を得る。新規タスク・定期スケジュール・外部サービス接続を作らない。
3. 変更前原本の保全と同一IDでの更新・読戻しが可能なことを確認する。未対応なら編集済みと装わず、必要な一操作だけ案内する。
4. 下記の手順を**秘書の現在有効な指示の末尾**に追加する。既存の秘書業務本文は書き換えない。設定先が外部スケジューラなどであり更新権限がなければ、KBの役割指示へ追記しても外部タスクまで反映したとは主張しない。

## 「日次バージョン確認」追記用の手順
- 秘書が実際に実行された日（登録済みの定期処理または利用者の手動呼出）に限り、**その日の最初の秘書応答**でだけ更新確認を試みる。時計だけでの自動実行は保証しない。
- `90_history/diary/YYYY/YYYY-MM-DD.md`（既存のその日の記録）に `ADNC_UPDATE_CHECK` のPASS行があれば、その日は**再検索しない**。同日の予定・本人タスクなど通常の秘書業務は省略しない。
- 未確認の場合はKBの `ADNC_INSTALLER_VERSION` と、GitHubの固定公開URL `https://raw.githubusercontent.com/Yosio-DMZ-C/AI-DODAI-Continuity/main/docs/updates/LATEST.json` を**実取得**する。対象は `track=installer` だけ。データの出典やスキーマのrevisionを版と混同しない。
- 両版を **X.Y.Z** の3整数として読み、上流のXまたはYがインストール版より上がっているときだけ通知候補。Zだけ変わったときは秘書から通知しない。上流が古い／値不正／取得失敗なら更新や通知をせずNOT_RUN等に区分し、必要以上に話題にしない。
- 前回の**実通知済み X.Y**は直近の秘書日記の `ADNC_UPDATE_CHECK` メタ行から引き継ぐ。同じX.Yを以前通知済みなら翌日も再通知しない。新しいX.Yが見つかった場合のみ「AD&Cに更新があります（導入版 → 新版）。更新内容を確認しますか？」の**一文**を本来の秘書報告の末尾に追加する。自動ダウンロード・更新・差分書込はしない。本人が更新を求めたらインストーラー§「導入済みKBの任意バージョン照合」に従い差分表と実行承認へ進む。
- 実際に取得・比較した日だけ既存の日記に次の短い1行を追加。翌日には `notified_minor` の最後の値だけ継承し、同日重複追記しない。例（実取得前に以下の例示値をPASSとして書かない）：

```md
<!-- ADNC_UPDATE_CHECK day=2026-10-25 status=PASS installed=1.4.0 latest=1.5.0 notified_minor=1.5 -->
```

- `notified_minor` は**最後に実際に利用者へ通知した**X.Y。通知がなければ直前の値を保ち、未通知は `none`。利用環境に日記保存権限がない場合は同一チャットの確認済み記録で可能な範囲だけ重複防止を行い、永続的な「1日1回保証」を主張しない。
- 既存の日記保存は元々承認済みの場合だけ。確認のためにユーザーの予定、タスク、公開GitHub、他アカウントのファイルを変更しない。GitHub Issue／PR／CIの監視は追加しない。

## 検収
- 変更前後の同一KB・NodeID・Drive fileIdを照合し、秘書の元の予定確認・日記・質問文が保持されたことを確認。
- `START_HERE`、更新対象の秘書指示、必要なregistryを**再取得**し、版・本文・参照整合がPASSになった場合だけインストーラー版を1.5.0へ確定。
- **静的な指示書更新 PASSと実運用動作PASSを区別する**。同日2回目の呼出、省略判定、X.Y変更の翌日再通知抑止、GitHub不可時NOT_RUNは、実際の秘書実行まではNOT_RUN。
