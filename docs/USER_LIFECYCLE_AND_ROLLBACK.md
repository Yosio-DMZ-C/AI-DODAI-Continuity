# AgentOS-C 利用停止・復帰・初期案内仕様（試験設計 v0.2）

- 作成日：2026-10-14
- 対象：利用者向け AgentOS-C の導入、試用、停止、復帰
- 状態：**設計承認・仕様の試験採用**。サービス横断の自動制御や日次初回判定の実装完了を意味しない。
- 原則：**導入前の状態を壊さず、利用停止を簡単にする**。元のAIの記憶や回答の雰囲気を完全復元できるとは保証しない。

## 1. 適用範囲と導入前の準備

- 初期導入はできるだけ試用チャット／プロジェクトに適用範囲を限定し、既存メモリ・カスタム設定を無断で消去・上書きしない。
- 変更前に、**取得可能で権限のある**カスタム指示・設定の旧値、AgentOS-Cの追加・変更箇所、KBとジョブの所在、復帰操作を記録する。取得できない元の状態は「未取得」と明記する。
- 外部KBはAIサービスの元の記憶と区別して保管する。利用停止をデータ削除と結び付けない。
- AIサービス側のメモリは利用中にも変化し得る。AgentOS-Cの利用をやめても、過去の会話やメモリの影響が完全に消えるとは限らない。

## 2. 状態と操作

| 状態 | 意味 | 動作 |
|---|---|---|
| `ON` | 利用中 | 許可された範囲でKBを参照・更新し、関連ジョブを利用 |
| `PAUSE` | 一時停止 | AgentOS-CのKB参照・更新・専用ジョブを止め、データは保持 |
| `OFF` | 利用終了 | AgentOS-Cの設定の適用を解除し、元の設定への復帰を試み、データは保持 |

- 自然言語の例：「AgentOS-Cを一時停止」「AgentOS-Cを再開」「AgentOS-Cの利用をやめる」。
- データ削除は別依頼とし、対象と影響を提示し、明示承認を得るまで実施しない。
- 停止・終了時は、AgentOS-Cに属する変更・ジョブだけを対象にする。関連性が不明な項目を推測で解除しない。
- 各操作について対象・実施結果・未対応・復帰経路を記録し、実行権限がない操作を「停止済み」と報告しない。サービス画面でしか変更できないものは人間向け手順を案内する。
- `PAUSE` から `ON` へ戻すときは権限と設定を再検証する。 `OFF` 後の再導入は利用者の再開指示に基づく。

## 3. 初期2利用日の案内

### 表示規則

- AgentOS-Cを**ONとして実際に利用した日を「利用日」**と定義し、初日と2日目の**各日最初の利用時の回答に1回だけ**案内を付ける。暦上の連続2日や48時間の経過ではなく、**最初の2利用日**とする。
- 利用日の境界は個人設定のタイムゾーンを使う。未設定なら利用者に確認できたタイムゾーンを使い、判断できなければ「日次初回」を断定せず案内状態を未確認とする。
- 見出しは**「ご案内:AgentOS-Cについて」**とする。通常の回答を妨げないよう短い案内を回答末尾に表示する。
- 同じ利用日に複数チャット／端末から起動しても、共有状態が確認できる場合は再掲しない。
- 「案内不要」等の明示指示があれば以後の案内を止める。これは利用停止やデータ削除の指示ではない。
- PAUSE/OFF中は表示しない。再開で初期案内の日数をリセットしない（再導入時にリセットするかは本人の選択）。
- 自動の時刻通知や、チャットを開くだけで回答が発生する機能を想定しない。**その日の最初のAgentOS-C対応回答**に付ける。

### 案内の最小本文

> **ご案内:AgentOS-Cについて**  
> AgentOS-Cは「一時停止」「再開」「利用終了」をいつでも指示できます。停止しても個人KBは削除しません。ただし、AIサービス本来のメモリや回答の雰囲気を導入前と完全に一致させることは保証できません。案内を止める場合は「案内不要」と伝えてください。

### 状態管理（論理仕様）

- 必要な状態：`lifecycle_state`、`onboarding_usage_dates`（最大2件の異なる利用日）、`onboarding_notice_dates`（表示済み日付）、`onboarding_notice_enabled`、`timezone`。
- 最初に当該利用日にONとして応答するとき、**既知の共有状態**を読み、表示対象なら応答に案内を添え、表示記録を更新する。失敗した場合は未検証とし、「今日初めて」等の保証をしない。
- 日次初回の厳密な重複防止には、複数チャットで共有される永続状態と、同時アクセスでも二重計上しない更新方法が必要。**AIへの指示文だけで横断的な1日1回表示は保証できない**。
- 共有状態が提供されない環境では、導入チャット内に限定した暫定動作を許容するが、全チャット・全端末での1日1回達成をPASSとしない。外部の定期ジョブでは代替しない。
- **保存先は新規作成を前提としない。** 既存の作業状態の正本を先に探し、利用状況を独立セクションに最小差分で追記できるか検討する。参照権限・書込権限・競合制御を検証するまでは正式運用に用いない。利用履歴を不要に公開しない。

### 既存の作業状態ファイルの再利用を優先する（2026-10-14 追補）

- **個人KBの既存設計との整合**：個人KBの統合設計では `BUILD_PLAN.md` が「今回の範囲、チェックポイント、再開位置」を持つ**作業状態の正本**と定義されている。既存利用者の実装候補として先に調べる。これは**全利用者・全AIサービスで `BUILD_PLAN.md` が存在するという意味ではない**。
- `AGENTOS_C_NEXT_20261009.md` は再開案内であり、作業状態全体の正本と断定しない。`START_HERE.md` は入口として扱い、日々の利用履歴の更新先にしない。
- **導入順序**：既存の状態記録を探索→本文と設計上の役割を確認→独立した小さなセクションで追加できるか確認→既存の作業内容に影響しない試験コピーで読取・書込・再読込を検証→複数チャットの同時更新を試験→正式利用を判断する。
- 既存の正本に書き込める場合、`lifecycle_state`、案内有効／無効、最初の2利用日と表示済み日のみを独立して記録する。**案内日を2行書いた事実だけで実表示成功としない**。既存の進行記録・履歴は書換えない。
- 既存ファイルの取得に失敗した場合は、検索結果名だけで不存在・用途不適と判断せず、**既知のファイルIDまたは入口文書から1度代替経路で読戻しを試す**。それでも読めない場合は `NOT_RUN` とし、利用者に不要な再添付を求めない。
- 異なるチャットが回答前に必ず同じファイルを読むことや、同時書込が衝突しないことは未検証。共有状態・排他制御がなければ**全チャットで1日1回表示を保証しない**。検証できない場合は導入したチャットに限定した暫定運用、または通知精度の緩和を検討する。
- 既存正本への追記が設計上不適切・書込不能・競合しやすい場合だけ、別ファイル／外部状態の追加を比較する。日付判定だけのために新しいDB・常駐プロセスを先に作らない。
- **個人KBと共通仕様を分ける**：本項の `BUILD_PLAN.md` は既存の個人KB運用における具体例。一般公開版には「利用者の既存の作業状態の正本を優先的に再利用する」という原則を適用し、個別ファイルの存在や共有権限を前提にしない。

## 4. 復帰検証ゲート

1. 導入前の設定スナップショットまたは「未取得」項目を明示。
2. AgentOS-CのKB参照・更新が止まったことを、**実際に操作できる範囲**で確認。
3. AgentOS-C専用ジョブの停止を確認、操作不能なら人間側の対応を残す。
4. 元の設定の復元結果を確認。不可逆なメモリ変更などは未復元として報告。
5. 個人KBは削除されていないことを確認し、再開手順を残す。
6. 実際のAIの回答の雰囲気は利用者にしか評価できず、設定の復帰だけで満足度のPASSとはしない。

品質状態は `PASS` / `FAIL` / `NOT_RUN`、対象外は理由付き `N/A` を用いる。確認不能を成功扱いしない。

## 5. 次の調査・実装対象

- AIサービスごとにカスタム指示、個人KB、メモリ、ジョブの制御可能範囲を区別し、停止・復帰可能項目を表にする。機能の存在と接続中のAIから操作可能かを混同しない。
- 2利用日の初回案内について、既存作業状態ファイルの実読取・試験コピーへの書込と読戻し、状態共有の有無、同時実行時の重複防止、案内不要設定、PAUSE→ONの継続、2利用日後の非表示をテストする。
- AI・人間の運用負担を見て、実装が過剰なら運用の簡略化を優先。サービスごとの別実装は必要になった場合だけ作る。

**変更対象外：** この設計の作成によって、既存の個人メモリ、実ジョブ、AIサービスのカスタム指示や権限、クラウド内のデータを変更しない。
