## 実証の開示基準

完全にPASSしていない機能を「導入できる」と保証しない。AIが「完了」と報告しても、実物の存在・JSON・参照・ファイル形式を独立確認する。未実施項目はNOT_RUNと記載する。

## PR投稿文の方向性（編集用）

**誘導先：** GitHub README → `docs/wiki/Home.md` → Quick Start → 設計書。

## 人間レビューの表示ルール

レビュー依頼時に、対象ファイルのソース差分ではなく**レンダリング済みページへの直接リンク**を最初に出す。レビューの対象・見る観点・返答方法を明記し、技術的検査を利用者に押し付けない。

| タグ | 意味 | 主担当 |
|---|---|---|
| **[人間確認]** | 実際の表示・読みやすさ・記述が意図どおりか確認 | 利用者 |
| **[人間判断]** | 採否・優先順位・公開可否など判断 | 利用者 |
| **[AI検査]** | 実ファイル、形式、リンク先、参照、内容、秘匿情報等を検査 | AI |
| **[未検証]** | 合格を宣言できない項目を理由付きで表示 | AI |

**運用原則：**

- タグには具体的な対象URLと確認観点を添える。単なる強調表示やリンク自体を依頼とみなさない。
- **「変更差分（Files changed）」を読むことを人間レビューの標準にしない**。MarkdownはGitHubのレンダリング表示、スライドは表示できる実物、Webページは公開相当のプレビューを使う。
- 「確認OK」または「修正：対象と内容」の返答で完結させる。GitHubでのApprove/チェックボックス操作は原則不要。
- AI検査と人間確認を分離し、人間の未実施をAIのPASSで代用しない。
- レビュータグはPR説明文・レビュー依頼・内部チェックリストで使い、一般向け本文に不要な確認用タグを残さない。
