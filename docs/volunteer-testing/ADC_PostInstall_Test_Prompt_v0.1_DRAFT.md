# AD&C 初期構築後テスト・検証レポート生成指示文（AI向け）

- 版：v0.1 / Draft（2026-10-18）
- 対象：AD&Cインストーラーの `実行` → 保存先選択 → 推奨案 → `進めて` を行った**同じAIチャット**。
- **用途**：完成したと報告されたKBを、観測可能な範囲で検証し、第三者が読みやすい**Markdownレポートを生成**する。[協力者向け検証ガイド](ADC_FirstTime_Test_Guide_v0.1_DRAFT.md)からの任意の追加手順。初回インストールの必須要件ではない。
- **禁止**：本指示だけを根拠に既存KBを作り直す、削除する、公開する、他人へ送信する、権限を変更する、購入する。検証を始めるために本番データを要求しない。

---

## 0. この指示を受け取ったAIが最初に行うこと

1. 直前の初期構築の会話・実行結果と、**実際に今読み取れる**生成ファイル・ZIP・テキスト・保存先を確認する。前のAIの「完成した」という文章を、検証成功の証拠として転記しない。
2. 使用インストーラー名・版、AIサービス名、無料／有料の申告、実際に利用できた接続機能・保存先の種類を記録。分からなければ `不明`。利用者が明示していない個人情報は推測しない。
3. 生成物がこのチャットから読めない場合は、検証用の最小ファイル（まずZIP／単一テキスト、または `START_HERE.md`・`BUILD_PLAN.md`・registry）を**1回だけ**添付依頼してよい。非公開の保存先を公開リンクへ変えるよう要求しない。提供されなければ該当試験は `NOT_RUN` とする。
4. **初期構築の記録／文書の静的確認／実物ファイル確認／利用者端末での受取**を独立した状態として記録する。必要最小限の調査・検査以外は追加しない。初期構築で提示した承認範囲を広げない。
5. チャット履歴の一部が利用不可なら「確認不可」。完了したふりをせず、その条件で可能な項目のみ検査する。

## 1. 必須の観測項目

状態は原則 `PASS` / `FAIL` / `NOT_RUN` / `N/A（適用外理由）`。**期待動作**と**実際の観測**を分け、証拠の種類（実ファイル読戻し／実際のツール応答／チャット履歴／AIの自己申告／人間の報告）を記録する。根拠不十分なら `NOT_RUN`。取得できない・検査できないことが確認できたなら、その段階に適切な `FAIL` または `NOT_RUN` を付け、理由を説明する。

|ID|検証点|PASS条件（実際に確認できた場合だけ）|
|---|---|---|
|I01|`実行` 直後の導線|保存先の選択を優先し、大量の設計質問を先行させなかった（履歴確認）。履歴不可ならNOT_RUN|
|I02|保存先・能力判定|選択した保存先と、AIによる直接の読み書きの可否を混同せず、方式を案内した|
|I03|推奨案と承認|初期案を原則1案だけ示し、`進めて` または相当の明示承認後に構築した|
|I04|実体の存在|作成ファイル、実際のZIP、または復元可能な相対パス＋全文テキストを**実読込**できた。文章だけならPASS不可|
|I05|必須入口|成果物の `START_HERE.md` と `BUILD_PLAN.md` 相当の本文を実際に読み、目的・入口・進捗または再開位置を確認できた|
|I06|登録台帳・ID|`00_system/registry.json` 相当を読み、JSON構文が有効で、NodeID（またはその仕様に沿う識別子）が記録されていた。単なるフォルダ名だけではPASS不可|
|I07|ファイル・参照整合|対象内のファイル一覧と入口参照が対応し、重複パス・明らかな参照切れがないことを確認した。全件走査不可なら範囲を明記|
|I08|初回の品質管理|BUILD_PLAN／レビュー等に、今回の対象・検査方法・PASS/FAIL/NOT_RUN・未完了が区別されていることを確認した|
|I09|保存と受取の区別|AI側の生成／梱包／受渡し／外部保存読戻し／本人の端末での受取を混同して報告していない|
|I10|秘密情報・公開境界|検証対象に分かる範囲で秘密値や無断公開を含まず、検証のために非公開KBの公開共有を要求しなかった。情報全体を検査できなければ検査範囲を限定|
|I11|構築完了の根拠|自称「完成」だけでなく、実ファイルと適用した必須検査の結果が対応する。必須FAIL/NOT_RUNが残る場合は完成品としない|
|I12|利用者負担|ユーザーが実際に行った操作／聞き直された質問／ダウンロード失敗等を履歴から確認できる範囲で記録。回数不明なら不明とする|

### 方式別に扱いを分ける

**A. 直接クラウド読書きが実際に可能な場合**
- 保存先の対象フォルダ内に作成された実ファイルの**存在・中身・識別子を再取得**する。権限や連携状態が確認できなければクラウド保存PASSにしない。
- 「APIで保存・読戻しができた」と「人間がアプリ上で開いた」は別。後者は本人からの報告がない限り `NOT_RUN`。

**B. AI無課金／制限モード（ファイルの受渡し＋手動バックアップ）の場合**
- ZIPを作れたなら**実ファイルを展開または一覧・本文照合**する。ZIPが利用できないAIでは、全相対パスと本文全文を含む単一MD/TXTの内容を確認する。
- `generated` → `packaged` → `delivered` → `externally_saved_confirmed` の状態を分離し、**利用者が外部保存したと確認できない限り最終段階にしない**。ZIP自体の生成に失敗しただけでは、代替テキストが有効なら方式全体のFAILにはしない。
- 別チャット読戻し・完全ZIP往復更新・AI間移植は**初期必須テストではない**。明示的に試した場合だけ別枠で結果を書く。

## 2. 任意の機能テスト（安全な架空データで行える場合のみ）

ここから先は**初期構築の成否と別評価**。更新できる方式かどうかをまず確認する。初期構築以外のKB変更には本人が今回許可した範囲のみを使い、無断でデータを追加しない。更新不可・拒否・容量制限なら `NOT_RUN` または `N/A` として元のKBを壊さない。

- **O01｜検索**：KB内の実在する項目を1件選び「何を記録したか」を問い、**当該ファイルを読んで**出典パスと照合。KBに情報がない場合はN/A（対象データなし）。
- **O02｜架空メモの追加→読戻し**：利用者がテストデータ追加に同意している新規の検証KBだけで、次の内容を1件登録して再読込する。

  ```text
  【架空のテスト情報】
  テーマ：青いノート計画
  決定済み：記録形式はMarkdown
  検討中：印刷用PDF
  未決定：メール自動送信
  ※これは架空情報であり、実際の所有・購入・承認・作業実績を示さない。
  ```

  確認事項：決定済／検討中／未決定を混ぜずに読めるか。元のNodeID・既存記録を維持したか。無料モードで**実際に完全版成果物を再出力できない**場合は、書換え完了の主張をしない。
- **O03｜別チャット・別AIへの持越し**：利用者が希望し、保存したKBファイルを新しい会話に**実際に渡せた場合だけ**、NodeIDと既存情報を照合。AI間の記憶自動継続は前提とせず、移行結果をこのチャットの自己申告で代用しない。

## 3. 人間による確認（AIの自己採点とは分ける）

レポート末尾に次の3点だけを簡潔に載せる。本人が未回答なら **未確認** のまま終了し、何度も催促しない。

- H01：`実行` のあと保存先の確認が最初だったか（はい／いいえ／不明）。
- H02：完成物を**人間が**端末または保存先で開けたか（はい／いいえ／未確認）。
- H03：KBの `START_HERE`・`BUILD_PLAN`・`registry` 相当が人間に確認できたか（全部／一部／未確認）。

### レポート作成時の注意

- **必須12項目すべてを確認したかのような表や点数を創作しない**。未検証の行は確実に残す。
- 人間の画面にファイルが現れているか／ダウンロードできるかは、AIの内部で確認できないことがある。利用者報告の有無を分ける。
- 追加の提案は最大1つ、余計な新機能や追加検証の要求を押し付けない。
- 作業環境・データが足りず重要ゲートがNOT_RUNなら **「検証完了・全項目合格」と言わない**。
- 外部送信・GitHubへの投稿・クラウドの公開設定変更はこの指示に含まれない。レポートはまず利用者本人へ渡す。
