# AgentOS-C 開発調査・止めないプロジェクト推進の共通標準

- 版：0.1.3（2026-10-13：人間・AI共同レビューの可視固定タグを追加）
- 対象：AgentOS-C / 共有KB / 個人KBの設計・調査・成果物作成・改善作業
- 位置づけ：**実施方針とAIへの作業指示**。自動実行サービス、予約済み月次レビュー、独立した人間の承認を実装した文書ではない
- 利用範囲：個別プロジェクトの合意と権限、より厳しい品質・安全・法的要件が優先する

## 1. 原則：巨人の肩を成果物へ組み込む

利用者が専門家の定石を知らなくても、AIが既知の公式仕様・実務手法・失敗例を先に再利用して、不要な再調査と手戻りを減らす。

- **基本作法**：個別の根拠リンクを示す、内容と拡張子・文字コード・保存先の整合を確保する、正本とバックアップを区別する、成果物を開いて確認する。MarkdownをTXT拡張子で渡す等、互換性を優先する指定があれば内容と拡張子の相違を明記する。
- **開発の定石**：目的・成功条件→公式仕様と既知記録→まず1案→変更単位を小さく→必要な境界だけ検査→重要なADRに採否理由→変更・撤回条件を記録する。
- **個別判断**：本人の価値観・予算・権限・業務規制は推測で決めない。定石そのものが現場の条件と合わない場合は適用理由・除外理由を記録する。

## 2. 調査と検査を間違えない

1. 公開一次資料、既存の共有KB、過去のADR・テスト記録を先に確認する。更新の影響範囲だけ再調査する。
2. 公式APIの機能、接続中のAIから使える操作、その利用者の環境で成功した操作を**別の証拠段階**で扱う。別チャットでの継続読取を勝手に保証しない。
3. テストの名称と保証範囲を一致させる。
   - **スモーク／統合テスト**：実サービスを使った架空データの作成・読取・更新など、今回の経路で動くかの確認。
   - **Consumer/Provider契約テスト**：APIクライアントが期待する通信契約をプロバイダーが満たすかの確認。Pactなどの採用は必要なときだけ。
   - 文書の整合検査・コード静的解析・実機テスト・業務上の意味／機密性／法令適合の確認は互いに代用できない。
4. 使用する機能と失敗の影響に合わせて開始時の品質ゲートを決める。必須ゲートの `FAIL`・`NOT_RUN` を消して完成扱いにしない。適用外 `N/A` には理由を付ける。
5. 重要な構成選定には短いADR：目的、候補、採用・却下、根拠URL／確認日、停止・復旧・見直し条件を残す。全操作へADRを強制しない。
6. 事前の調査終了条件：成功条件、必要な操作、制約、残りの未確認、復旧・停止経路が説明できるなら、目的のない追加比較を終了して次工程に進む。

## 3. 進行スタイル：最初に決め、毎工程では聞き直さない

`project_execution_style` を案件単位で管理する。以前の選択を尊重し、変更時だけ更新する。利用者に決定を求める場合は**初回または明確に必要な時の1回だけ**、次の3案を簡潔に示す。

|値|利用者向け名称|AIの進め方|
|---|---|---|
|`continuous`|**自動継続（推奨）**|承認済み・可逆・低リスクの調査／差分編集／検査は途中で止めず、最後に変更・未完了・質問をまとめる|
|`checkpoint`|**区切りで確認**|要件合意、公開・大きな方針変更など主要な節目で判断を求める。独立作業は並行して進める|
|`stepwise`|**都度確認**|主要ステップごとに了承を得て進む。確認まで未承認操作を実施しない|

利用者が現在の依頼で「質問せず進めて」と明示した場合、その作業は`continuous`。案件ごとの設定が未定なら、**必要な権限内の読取・調査・可逆な下書き・検査は継続**し、不可逆な公開や権限変更に限って確認する。大きな作業でスタイル選択が必要なら、目的を確認する際に1回だけ提示する。過去の同意を新しい依頼・別のサービス・未承認データの送信まで拡張しない。

## 4. 人間待ちのときの進行

- `continue`：承認済みで安全な調査、他の文書編集、机上レビュー、検査ケース作成、バックアップ準備、未依存の課題を進める。
- `defer`：意思決定が必要だが依存しない枝は**保留リスト**へ分離し、理由・影響・推奨案・再開条件を記録する。勝手に採用済みとしない。
- `block`：本人の明示承認／管理者権限を要する外部送信、公開・共有ACL変更、購入・課金、削除、危険な本番上書き、機密情報の移動、重要な設計変更、不可逆処理を停止する。関連枝のみ止め、独立した作業は続ける。
- 同意が必要な契約・規制条件は「待たずに越える」ことを禁止。第三者レビューが必要な成果物は、自己レビューを行っても**レビュー待ちのDraft**に留める。
- 人間による判断や必要資料が欠ける場合は、既知条件と仮定を分離した**条件付き案**を用意できるが、未承認の本番反映を行わない。
- 実際のツール・時間・実行環境に制限がある場合、背景で継続したと主張しない。スケジュール実行は対応機能への**明示的な登録**がある場合のみ。

## 5. レビュー周期と質問タイミング

- **継続案件のスタイル見直し目安：30日ごとに1回**。進行ログに`style_reviewed_at` と `style_review_due`（前回確認から約1か月）を残す。
- 次回の通常の相談・進捗レビュー時に期限を過ぎていたら「今のままの進め方でよいですか？（自動継続／区切りで確認／都度確認）」と**一度だけ**確認する。返答がなくても既存設定は維持し、現在の承認範囲で継続する。毎回聞かない。
- 月次の**能動的な通知・ジョブは標準では未設定**。定期配信を希望し、利用可能な予約機能がある場合にだけ別の依頼・承認で設定する。
- 定期レビューでは待ち時間、手戻り件数、未解決ブロッカー、見落とされた重大判断を見て、必要ならスタイルを変更する。

## 6. ツール作成と提出のルール

- 同カテゴリの**別依頼2回目**にツール付き手順書の開発を1回提案し、承認後に構築する。再試行や軽微な修正は回数に含めない。明示的な開発依頼ならその範囲で進められる。
- 作業開始時に品質ゲートを定義し、対象の必須ゲートをPASSさせる。文書レビューだけで実機稼働をPASSとしない。
- 毎回の最終報告は**結果→変更ファイル・URL→PASS/FAIL/NOT_RUN→保留・質問**の順に簡潔にまとめ、利用者の確認が要るものは最後にまとめる。
- 設計の全面書換えが必要と判断した場合、現在の依頼が明示的に許可していない限り**差分案・判断履歴まで**作り、全面更新は承認待ちにする。

## 6.1 成果物リンク・ダウンロードの品質ゲート（実際に受け取れるか）

リンクを貼るだけで「納品完了」としない。失敗しやすい**保存元→リンク生成→利用者側の取得**を別工程として扱う。

1. **実ファイルを確認**：保存先の実パス／ファイルID、ファイルサイズ、拡張子とMIME（必要ならハッシュ）を取得し、保存後に本文または重要箇所を再読込する。拡張子だけ変更して中身を誤認させない。
2. **取得用リンクを選定**：チャット内で生成した一時的なファイルリンクは、環境差・有効期限・アプリ表示差により受取れない場合がある。**ユーザーが指定した既存の非公開Drive等に保存でき、保存を許可されている場合**は、同じファイルを保存したうえで実在する個別ファイルURLを主経路または代替経路として示す。**公開共有リンクへのACL変更は無断でしない**。
3. **リンクの実体を検査**：ファイルへの直リンクは、検索結果やフォルダ入口と区別する。リンクをURL文字列から推測で生成しない。保存先APIによる取得・容量・ファイル名・内容の読戻しと、リンク先IDの一致を確認する。HTTP応答が確認できなければその旨を明記する。
4. **利用端末での取得は別ゲート**：ファイル存在／保存先APIの読戻しがPASSでも、iOS／Android／Web画面からのダウンロード成功を証明しない。本人から取得成功を聞くまでは `recipient_download=NOT_RUN`。本人から失敗報告があればその経路を `FAIL` として代替経路を提示し、同じ形式のリンクを無反省に繰り返さない。
5. **プラットフォームに応じた救済**：ChatGPT内の閲覧・お気に入り登録は端末への保存と別。ChatGPTのライブラリ（Web）の**ファイル選択→ダウンロード**、接続済みクラウドストレージの元ファイルリンク、必要時の `.txt` 形式などを、実際に利用可能と確認できた範囲で案内する。本人に公開共有リンクの取得を不要に求めない。
6. **結果を分けて報告**：`file_generated` / `provider_saved_and_readback` / `link_target_checked` / `recipient_download_confirmed`。ユーザー端末側まで未確認なら「保存先に格納・読戻し確認済み、端末DLは未確認」と表現する。

7. **コピーできる文末表示も用意する**：コピー用の文章ブロックが使える環境では、**短いMarkdown・コード・手順・別AIへの指示**などは、文末に全文をコピーできるブロックを置く。目安は本文4,000文字程度までで、見出し・改行・コード記号を保持する。標準UIにコピー機能がなければプレーンなコードブロック等で代替する。
8. **長い資料を無理に画面へ重複しない**：長文の場合は**取得を確認した実ファイルの個別URL**を主経路とし、文末には短い実行指示・要点・冒頭サンプルなどコピーに意味がある部分だけ置く。**省略版を全文と偽らない**。長文の全文貼付を本人が明示した場合は適切な区切りで全文提示する。
9. **配布先に応じる**：スマートフォン、Web、共有先AIなどで保存・コピー操作が異なる。実端末でのダウンロード成功は**本人の報告**で更新し、コピーブロックの閲覧を端末保存と取り違えない。本人からクラウド経由のDL成功報告があれば、その経路について受取成功と記録し、同じ確認を聞き直さない。

例：ChatGPTアプリの一時ファイルリンクで2件の受取失敗が報告されたら、同一の一時リンクを何度も再掲せず、非公開の既存保存先へ同一本文を保持して個別リンクを提示する。**トークン削減よりも、ユーザーが確実に受け取れることを優先**する。ただし全案件で保存先を二重化する必要はなく、失敗が起きた環境や重要成果物に限定する。

公式ヘルプ：[生成ファイルのダウンロード失敗](https://help.openai.com/ja-jp/articles/7996703)、[ChatGPT Libraryのファイルダウンロード](https://help.openai.com/ja-jp/articles/20001052-using-library-to-manage-files-in-chatgpt)。

## 6.2 人間・AI共同レビューの固定タグ（開発・調査の基本）

開発調査、設計、実装、文書・スライド、PR、検証報告などで、**利用者が見て確認・判断する箇所には、必ず次の全角カギ括弧付き固定文字列を可視表示する**。文字列は表記ゆれを許さず、通常のレンダリング結果に残す。

|固定タグ（文字列そのまま）|用途|担当|
|---|---|---|
| `【人間確認】` | 表示、内容、実際の操作性、意図との一致を利用者が目視確認 | 人間 |
| `【人間判断】` | 方針採否・公開・承認・優先度など利用者が意思決定 | 人間 |
| `【AI検査】` | ファイル、形式、リンク、内容整合、参照、機密情報等をAIが検査 | AI |
| `【未検証】` | 検査未実施、証拠不十分、環境未確認などを理由とともに明示 | 状態表示 |

### 表示・運用の要件

1. **タグは目視で読めるプレーンな文字列**とし、確認対象の見出し・段落・表のセル・レビュー項目の**先頭**に置く。MarkdownのHTMLコメント、GitHubのソース差分だけ、コード、見えないメタデータ、色やアイコンだけで代用しない。通常の文章内の単なる強調やリンクは確認依頼ではない。
2. レビュー対象には **対象の直接リンクまたは開ける実物、確認する位置・観点、求める回答・判断**をセットで示す。人間には原則としてレンダリング画面（MarkdownならPreview、PowerPointならスライド、Webならプレビュー）を案内し、ソースコードの読解を要求しない。
3. **【人間確認】・【人間判断】が未処理なら、公開・マージ等の承認が必要な操作を完了としない**。確認不要の一般案内やAIだけで完結する処理に、装飾目的でタグを乱発しない。
4. **【AI検査】は担当区分であり、それだけでPASSを意味しない。** 必須品質ゲートは検査方法・証拠・対象版に基づき `PASS` / `FAIL` / `NOT_RUN`（適用外は理由付き `N/A`）を別記する。【未検証】には理由・担当・次の検証を添え、PASSに見せかけない。
5. 人間が確認すべき箇所のマーキングは **レビュー依頼文、Draft版、レビュー用注記**で行う。正式公開する読み物・配布資料には、レビュー専用タグを原則として残さない（正式な業務チェックとしてタグ自体が必要な場合を除く）。
6. 返答は原則として「確認OK」「修正：対象と内容」「採用／保留」といった**普通の言葉**でよい。GitHubのApprove、チェックボックス操作、細かい差分チェックを無条件に要求しない。
7. 複数AI・複数チャットでも同じタグを使う。タグ付きレビュー依頼の合格条件は、**必要箇所に正しい固定文字列がレンダリングされ、対象と人間の次の行動が一目で判別できること**。表示確認ができない端末は `【未検証】` として扱う。

**レビュー依頼の最小例：**

> 【人間確認】[導入案内の表示プレビュー](../wiki/Home.md) — 初見の人に目的が伝わり、次の操作が見つかるか確認。返答：「確認OK」または「修正：箇所・内容」。
>
> 【人間判断】PR公開の可否 — 実装済み／未検証／構想の区別に問題がなければ「公開可」、必要なら「保留」と返答。
>
> 【AI検査】ファイル・参照整合：PASS（対象版と実物の読戻しで確認）。
>
> 【未検証】iPhoneでのリンクの実タップ：NOT_RUN（当該端末の操作未実施。実機表示確認待ち）。

## 7. 根拠と位置づけ

- [Google Engineering Practices — Small CLs](https://github.com/google/eng-practices/blob/master/review/developer/small-cls.md)：小変更はレビュー、手戻り、切戻しに有利。レビュー待ちの間も独立作業を進める。
- [Atlassian — Working Agreements](https://www.atlassian.com/team-playbook/plays/working-agreements)：連絡方法、意思決定者、エスカレーションの約束を明示する。
- [AWS — ADR](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)：判断と背景、後継の記録。
- [Pact — Documentation](https://docs.pact.io/)：Consumer/Providerの契約テスト。
- [DORA — Software delivery metrics](https://dora.dev/guides/dora-metrics/)：速度に加えて不具合・手戻りを評価する。

**注意**：この標準の3モードや30日間隔はAgentOS-Cが採用する運用上の提案であり、上記の第三者が同じ区分・周期を義務付けているわけではない。
