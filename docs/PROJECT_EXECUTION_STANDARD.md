# AgentOS-C 開発調査・止めないプロジェクト推進の共通標準

- 版：0.1.16（2026-10-28：専門プレイブックの調査順・停止条件を一般検索より優先。0.1.15までの規定を保持）
- 対象：AgentOS-C / 共有KB / 個人KBの設計・調査・成果物作成・改善作業
- 位置づけ：**実施方針とAIへの作業指示**。自動実行サービス、予約済み月次レビュー、独立した人間の承認を実装した文書ではない
- 利用範囲：個別プロジェクトの合意と権限、より厳しい品質・安全・法的要件が優先する

### AIインターフェースの共通入口（2026-10-26 β）

**目的**：AIに何を記憶させるかではなく、**判断の瞬間に、既存の原則・文脈・道具が自然に参照される順路**を設計する。文脈ゲート（判断前の前提整理）・道具棚（実行手段の発見）・完了ゲート（実物による結果検査）は別機能とし、新しい独立DBや長い起動儀式は作らない。

- **固定コア（省略不可）**：今回の依頼、採用済み制約、禁止・承認境界、目的／完了条件、必要な検査。毎回正本全文を読み直すという意味ではなく、短い入口と現行正本参照で適用する。未取得の事実を読了・確定扱いにしない。
- **変更依頼の基本動作（必須）**：「変更して」「直して」「採用して実装して」等は、特段の『相談・案のみ』指定がない限り、提案・Draft作成ではなく**利用者が求めた最終状態への実装依頼**として受け取る。実装対象・影響先・承認境界を短く確定し、正本書込直前に**「変更を実装しますね？」**と確認する。本人の承認後は現行正本と必要な個別手順・参照・台帳・Git等を実際に更新し、読戻し・必要な実行検査まで行う。実装不能や未承認の工程があれば未完了として残し、案やPRだけを「変更完了」と呼ばない（§6.3.2〜§6.3.3）。
- **Skill別プロファイル**：各実行型Skillの冒頭数行に、今回の仕事で読む「依頼の文脈」と「本人の好み・環境設定」の既定深度を **深く読む／要約だけ／存在だけ知る** から指定する。深度選択の既定はSkill側で定め、例外は仕事の事実に応じて対象だけ見直す。詳細な共通規定をSkillごとに複製しない。
- **本人の正本**：記録済み本人設定および今回の明示指示を優先し、本人の好み・個人KBの秘密情報は公開Skillや公開ログへ転載しない。大きな文化区分などは本人の記録が無いときの暫定的な背景にとどめ、個人についての確定根拠にしない。
- **道具棚**：既存の道具・原本へ到達する短いリンクをSkillの実行順路へ置き、用途に合わない道具の利用は強制しない。取得不能な実体を「利用可」と書かない。
- **証跡と完了**：適用する案件では、実際に取得したコア・文脈・設定・道具を既存記録に1行で残す（秘密値・非公開IDは公開しない）。重大判断の直前に関係規則を再参照し、§2・§6.3の品質ゲートを維持する。Skill自体へ到達できなかった場合は文脈ゲート通過とみなさない。独立AIの自発的到達・利用者負担削減は別試験であり、文書反映だけではPASSにしない。

## 0. AD&C全体のβ開発と「うまく失敗する」運用（2026-10-23）

**対象はAD&Cの全機能・全担当・開発成果物と導入後の運用**。βは「利用者へ影響する全処理が安全／完成」を意味しない。**低リスクで可逆なことは、検証を終えるまで実装を止めず、小さく試して失敗を観測・修正する**。重大な権限変更・公開・外部送信・課金・削除・本番不可逆操作は、従来どおり本人の承認と個別の安全確認が必要。全操作を重い審査や人間の都度確認に戻さない。

**βの失敗回復契約（変更があるときだけ、既存のBUILD_PLAN／PR／作業ログに最小記録。新DB・常駐ジョブ不要）：**

1. **変更前の足場**：対象と許可範囲、変更前の取得済みID／版／hashまたは設定値、原本・復元元、やめる条件を確定する。取れない場合は推測で「復元可能」と宣言せず、影響の小さい試験コピーから始める。
2. **小さく実装**：可逆な1差分を実行し、結果を実物から読み直す。効果や対象を限定して **β試用中／動作PASS／効果NOT_RUN** 等を分ける。完成・本番運用の必須品質ゲートは緩めないが、実装・試用の開始をすべての効果検証完了まで保留しない。
3. **失敗を検知したら局所停止**：原因を推測で隠さず、失敗した操作・残った変更・成功済みの部分・未確認の副作用を分ける。独立して安全な作業は続け、同じ失敗をただ繰り返さない。
4. **安全に戻す／進め直す**：現在の対象版が想定どおりか再取得してから、その差分だけ復元する。Gitは**旧状態を戻す新コミット**、KBは既存§13の旧版・バックアップとID／参照を確認して差分復旧。競合を検出したら他者の更新を上書きせず対象だけ保留。戻した結果も読戻しで確認し、失敗自体の記録と教訓は消さない。
5. **戻せないものを区別**：送信済みメール、公開済み情報、課金、削除、元のAIメモリ、外部サービスの作用はGitの巻戻しで元に戻らない。事前の承認／小さな模擬試験を維持し、必要なら訂正・公開撤回・補償・人間への報告を個別に扱う。
6. **通常の会話は維持**：成功にも失敗にも過適応せず、作業の節目にだけ現行目的・AD&Cの関連規定へ軽く戻る。無関係なリセット、定型ログ表示、手動整理を利用者に強いない。負担が増えるβ機能はまず停止・縮小し、必要なら元に戻す。

**最小の失敗時報告**：`対象／試した変更／実際の結果（PASS・FAIL・NOT_RUN）／現在残っている変更／復元結果／次に進める1手`。成功時に毎回これを表示しない。既存の証拠やログに記録できるなら重複文書を作らない。利用停止は§6.0.2と[利用停止・復帰仕様](USER_LIFECYCLE_AND_ROLLBACK.md)の`PAUSE`／`OFF`を参照する。**GitHubに記述しただけでは他のAI・チャットへの自動配信や効果を証明しない**。

### 未完了を消さないタスク捕捉・中断引継ぎ（2026-10-25採用）

**「検討を始めた／実装を引き受けた／本人の依頼を受けた」時点で、続きの作業が存在するなら着手前に登録する。** すでに同じ目的のタスクがあれば新設せず既存IDへ追加。作業の途中で工具・接続・PR・CI・承認が止まった場合も、**報告して会話を終える前に、必ずそのタスクの現行状態を書き戻す**。設計への賛同だけ、PRを作っただけ、レビュー待ち、CIのPASS、PRのClosed/Mergedはタスク全体のDONEにならない。

**正本は一件一か所**：公開可能なAD&C開発案件は既存[Issue #13](https://github.com/Yosio-DMZ-C/AI-DODAI-Continuity/issues/13)の`ADNC-T...`行を使用し、詳細・PR・実物はリンク。個人の用事・非公開案件は本人の**既存個人KBのTASKS／Project Context／BUILD_PLAN**を正本とし、公開GitHubへ内容・ID・非公開URLを転載しない。両方で関係する場合は、公開側に個人情報を含まない進行状態だけ記し、私的内容を複製しない。新DB、新しい全件台帳や定期タスクは作らない。

**最小のタスク行・中断チェックポイント**：`task_id｜依頼・完了条件｜担当｜状態｜対象PR/成果物の正本リンク｜実施済みと検収証拠｜未完了の1工程（次の担当・再開条件）｜最終確認日`。不足情報は`NOT_RUN`。状態は既存の`PROPOSED / READY / IN_PROGRESS / REVIEW_PENDING / BLOCKED / DONE / DROPPED`等を維持し、**DONEまたは理由付きの明示DROPPEDになるまで「要追跡」のフラグを落とさない**。進捗・検査の`PASS/FAIL/NOT_RUN`はタスクのライフサイクル状態と別の軸。意図的に取り下げた案件は勝手にDONEとせず、理由と判断主体を保存してDROPPEDとする。

**完了／中断の出口**：本人が求めた完成条件を実物で確認し、保存先・受渡し・必要な動作が検収できた範囲だけDONE。PRが安全チェックで止まった／閉じた／別枝へ移された場合は、作業本体が未達なら**BLOCKEDかIN_PROGRESSに保持**し、何が通ったか・失敗点・次に試す1工程・戻し方を残す。担当チャットが変わる時は、次担当がタスクIDだけで当該正本に辿れるかを確認。タスク一覧へアクセスできなければ登録や読取の成功を偽らず、当該引継ぎは`NOT_RUN`と報告し、本文の引継ぎ案を本人に渡す。

**見る側の責務**：開発リーダーは作業開始時と引継ぎ時、Issue #13冒頭の「未完了・要追跡」を必要範囲で読む。秘書は**利用許可・接続がある場合に限り**、本人の既存TASKS／Project Contextに加え、必要時にはIssue #13の**表示上の未完了案件だけ**を見て、既にDONEの案件を催促せず、止まっている重要案件を簡潔に拾う。開発IssueやPRの全件巡回、開発作業の代行、毎朝全件列挙は求めない。対象正本へアクセスできないときは気づいたふりをしない。外部AIへはこの入口の提示／実取得が必要であり、GitHubの記述が自動配信されるわけではない。

## 1. 原則：巨人の肩を成果物へ組み込む

利用者が専門家の定石を知らなくても、AIが既知の公式仕様・実務手法・失敗例を先に再利用して、不要な再調査と手戻りを減らす。

- **基本作法**：個別の根拠リンクを示す、内容と拡張子・文字コード・保存先の整合を確保する、正本とバックアップを区別する、成果物を開いて確認する。MarkdownをTXT拡張子で渡す等、互換性を優先する指定があれば内容と拡張子の相違を明記する。
- **開発の定石**：目的・成功条件→公式仕様と既知記録→まず1案→変更単位を小さく→必要な境界だけ検査→重要なADRに採否理由→変更・撤回条件を記録する。
- **個別判断**：本人の価値観・予算・権限・業務規制は推測で決めない。定石そのものが現場の条件と合わない場合は適用理由・除外理由を記録する。

## 2. 調査と検査を間違えない

1. 公開一次資料、既存の共有KB、過去のADR・テスト記録を先に確認する。更新の影響範囲だけ再調査する。
   - **調査順序の優先**：対象業務に実取得できる専用プレイブックがあれば、一般的な網羅検索よりも**その検索順序・採否ゲート・終了条件を優先**する。原型が採用できた段階で無目的な横断探索をやめ、**不足項目に限定して追加調査**する。一般知識の確認は必要なところだけ行い、**安全・法令・規制など実施可否を左右する必須の検査は省略しない**。専門手順が未取得なら、存在・適用を推測で主張せず取得・参照できる範囲の確認に戻す。
2. 公式APIの機能、接続中のAIから使える操作、その利用者の環境で成功した操作を**別の証拠段階**で扱う。別チャットでの継続読取を勝手に保証しない。
3. テストの名称と保証範囲を一致させる。
   - **スモーク／統合テスト**：実サービスを使った架空データの作成・読取・更新など、今回の経路で動くかの確認。
   - **Consumer/Provider契約テスト**：APIクライアントが期待する通信契約をプロバイダーが満たすかの確認。Pactなどの採用は必要なときだけ。
   - 文書の整合検査・コード静的解析・実機テスト・業務上の意味／機密性／法令適合の確認は互いに代用できない。
4. 使用する機能と失敗の影響に合わせて開始時の品質ゲートを決める。必須ゲートの `FAIL`・`NOT_RUN` を消して完成扱いにしない。適用外 `N/A` には理由を付ける。
5. 重要な構成選定には短いADR：目的、候補、採用・却下、根拠URL／確認日、停止・復旧・見直し条件を残す。全操作へADRを強制しない。
6. 事前の調査終了条件：成功条件、必要な操作、制約、残りの未確認、復旧・停止経路が説明できるなら、目的のない追加比較を終了して次工程に進む。

## 3. 進行スタイル：最初に決め、毎工程では聞き直さない

`project_execution_style` を案件単位で管理する。以前の選択を尊重し、変更時だけ更新する。利用者に決定を求める場合は**初回または明確に必要な時の1回だけ**、次の3案を簡潔に示す。

|値|利用者向け名称|AIの進め方|
|---|---|---|
|`continuous`|**自動継続（推奨）**|承認済み・可逆・低リスクの調査／差分編集／検査は途中で止めず、最後に変更・未完了・質問をまとめる|
|`checkpoint`|**区切りで確認**|要件合意、公開・大きな方針変更など主要な節目で判断を求める。独立作業は並行して進める|
|`stepwise`|**都度確認**|主要ステップごとに了承を得て進む。確認まで未承認操作を実施しない|

利用者が現在の依頼で「質問せず進めて」と明示した場合、その作業は`continuous`。案件ごとの設定が未定なら、**必要な権限内の読取・調査・可逆な下書き・検査は継続**し、不可逆な公開や権限変更に限って確認する。大きな作業でスタイル選択が必要なら、目的を確認する際に1回だけ提示する。過去の同意を新しい依頼・別のサービス・未承認データの送信まで拡張しない。

## 4. 人間待ちのときの進行

- `continue`：承認済みで安全な調査、他の文書編集、机上レビュー、検査ケース作成、バックアップ準備、未依存の課題を進める。
- `defer`：意思決定が必要だが依存しない枝は**保留リスト**へ分離し、理由・影響・推奨案・再開条件を記録する。勝手に採用済みとしない。
- `block`：本人の明示承認／管理者権限を要する外部送信、公開・共有ACL変更、購入・課金、削除、危険な本番上書き、機密情報の移動、重要な設計変更、不可逆処理を停止する。関連枝のみ止め、独立した作業は続ける。
- 同意が必要な契約・規制条件は「待たずに越える」ことを禁止。第三者レビューが必要な成果物は、自己レビューを行っても**レビュー待ちのDraft**に留める。
- 人間による判断や必要資料が欠ける場合は、既知条件と仮定を分離した**条件付き案**を用意できるが、未承認の本番反映を行わない。
- 実際のツール・時間・実行環境に制限がある場合、背景で継続したと主張しない。スケジュール実行は対応機能への**明示的な登録**がある場合のみ。

## 5. レビュー周期と質問タイミング

- **継続案件のスタイル見直し目安：30日ごとに1回**。進行ログに`style_reviewed_at` と `style_review_due`（前回確認から約1か月）を残す。
- 次回の通常の相談・進捗レビュー時に期限を過ぎていたら「今のままの進め方でよいですか？（自動継続／区切りで確認／都度確認）」と**一度だけ**確認する。返答がなくても既存設定は維持し、現在の承認範囲で継続する。毎回聞かない。
- 月次の**能動的な通知・ジョブは標準では未設定**。定期配信を希望し、利用可能な予約機能がある場合にだけ別の依頼・承認で設定する。
- 定期レビューでは待ち時間、手戻り件数、未解決ブロッカー、見落とされた重大判断を見て、必要ならスタイルを変更する。

## 6. ツール作成と提出のルール

- 同カテゴリの**別依頼2回目**にツール付き手順書の開発を1回提案し、承認後に構築する。再試行や軽微な修正は回数に含めない。明示的な開発依頼ならその範囲で進められる。
- **人が実行するスクリプト・配布キット／手順書を作る・重要改訂する入口**：利用者が起動するスクリプト、ZIP等の実行キット、実行手順書・Runbook・実務Skillを作成または重要改訂するときは、着手時に本書の **§6.3.2「1タスク・1実行正本」と人間向け操作導線、および§6.3.3「実行指示書の品質基準」**を実際に読み、完成条件→実行入口・正本・素材→工程→実物検収をつなぐ。入口が異なる個人KB・配布インストーラー・共有テンプレートからもこの同じ正本へ参照を張る。取得できない環境では既知の概要だけで品質適合を宣言せず、該当検査を `NOT_RUN` とする。小改訂は影響部分のみ検査し、AI内部だけの一時処理へ配布UIを強制しない。
- 作業開始時に品質ゲートを定義し、対象の必須ゲートをPASSさせる。文書レビューだけで実機稼働をPASSとしない。
- 毎回の最終報告は**結果→変更ファイル・URL→PASS/FAIL/NOT_RUN→保留・質問**の順に簡潔にまとめ、利用者の確認が要るものは最後にまとめる。
- 設計の全面書換えが必要と判断した場合、現在の依頼が明示的に許可していない限り**差分案・判断履歴まで**作り、全面更新は承認待ちにする。

## 6.0 実行環境と言語の選択

- **実行環境を優先**：人間に渡すツールは、対象OSで追加インストールせず実行できる方法を第一候補とする。OS名だけで言語を固定しない。
- **個人KBの設定を優先**：利用者のOS、利用可能な実行環境、優先言語、追加インストール可否、業務上の制約を、確認できた範囲で個人KBに記録・再利用する。指定があれば尊重し、未確認事項を推測で埋めない。変更時だけ更新する。
- **AI自身が実行する場合**：AIの実行環境で実際に利用できる言語を選ぶ。Pythonは有力候補だが、コード生成能力と実行能力を区別し、実行不可なら代替経路を選ぶ。
- **共通仕様と検査**：入力、出力、判定条件、品質ゲートは実装言語から分離する。複数言語版は必要になった場合だけ作り、各実装の実行検査を別々に記録する。
- **運用と更新**：この節は現時点の選択方針であり、各OS・AIサービスの対応表や移植実装を今すぐ整備する義務を生じさせない。必要が出た際に最小差分で更新する。

## 6.0.1 一時成果物の命名・整理（試験運用）

- 一時成果物の新規ファイル名は `人間向け名称__系列ID_種別_版_状態_日付.拡張子` を推奨する。人間向け名称は**文字数制限なし**とし、`__` は含めない。`__` を唯一の境界として管理コードを解析し、文字数検査や空白埋めは行わない。
- 例：`調査報告ツール__RRB_TOOL_v002_DRAFT_20261014.zip`。系列IDと種別は英大文字・数字で固定し、版は `v` + 3桁以上の数字、日付は `YYYYMMDD`。状態は `DRAFT` / `UNVERIFIED` / `REVIEWED` / `CANONICAL` を基本とする。
- 同系統の判定は**系列ID＋種別**で行う。人間向け名称の類似や先頭数文字だけで旧版と断定しない。版が同じ場合は日付だけで後継版とみなさず保留する。
- **ファイル名の状態は自己申告**であり、実際の品質ゲートや正本保存・読戻しの証拠に代わらない。重要情報の正本への引継ぎ、後継版の読戻し、保護指定、削除ログを確認できないファイルは削除しない。
- TEMPは正本ではない。30日経過は**点検の目安**であり自動削除期限ではない。新規作成分から適用し、既存ファイルの一括改名はしない。
- 初期段階は**分類・削除候補の抽出のみ**を行う。ゴミ箱移動・完全削除・公開権限変更は実行しない。自動整理への移行は分類精度と復元経路を検証して別途承認を得る。
- 月次レビューは既存の実行機会を活用し、定期ジョブの登録や専用ツール開発を必須としない。

## 6.0.2 利用停止・復帰と初期案内（試験運用）

- AgentOS-Cを一時停止（`PAUSE`）・再開（`ON`）・利用終了（`OFF`）できる設計を基本とし、**利用停止と個人KBの削除を分離**する。導入前の変更状態を記録し、復帰できる範囲・できない範囲を明示する。
- **最初の2利用日**のそれぞれ**その日最初のAgentOS-C利用への回答に1回だけ**、見出し「**ご案内:AgentOS-Cについて**」で、停止・再開・利用終了の方法と復帰保証の限界を短く案内する。「案内不要」で以後の表示を止める。
- チャット横断の日次初回判定には永続的な共有状態が必要。指示文だけでの厳密な重複抑止やAIサービスの元メモリの完全復元は保証しない。**仕様の採用と実装の動作確認を区別**する。
- 詳細は[利用停止・復帰・初期案内仕様](USER_LIFECYCLE_AND_ROLLBACK.md)を正とする。個別AIサービスの制御方法や追加実装は検証後に決める。

## 6.1 成果物リンク・ダウンロードの品質ゲート（実際に受け取れるか）

リンクを貼るだけで「納品完了」としない。失敗しやすい**保存元→リンク生成→利用者側の取得**を別工程として扱う。

1. **実ファイルを確認**：保存先の実パス／ファイルID、ファイルサイズ、拡張子とMIME（必要ならハッシュ）を取得し、保存後に本文または重要箇所を再読込する。拡張子だけ変更して中身を誤認させない。
2. **取得用リンクを選定**：チャット内で生成した一時的なファイルリンクは、環境差・有効期限・アプリ表示差により受取れない場合がある。**ユーザーが指定した既存の非公開Drive等に保存でき、保存を許可されている場合**は、同じファイルを保存したうえで実在する個別ファイルURLを主経路または代替経路として示す。**公開共有リンクへのACL変更は無断でしない**。
3. **リンクの実体を検査**：ファイルへの直リンクは、検索結果やフォルダ入口と区別する。リンクをURL文字列から推測で生成しない。保存先APIによる取得・容量・ファイル名・内容の読戻しと、リンク先IDの一致を確認する。HTTP応答が確認できなければその旨を明記する。
4. **利用端末での取得は別ゲート**：ファイル存在／保存先APIの読戻しがPASSでも、iOS／Android／Web画面からのダウンロード成功を証明しない。本人から取得成功を聞くまでは `recipient_download=NOT_RUN`。本人から失敗報告があればその経路を `FAIL` として代替経路を提示し、同じ形式のリンクを無反省に繰り返さない。
5. **プラットフォームに応じた救済**：ChatGPT内の閲覧・お気に入り登録は端末への保存と別。ChatGPTのライブラリ（Web）の**ファイル選択→ダウンロード**、接続済みクラウドストレージの元ファイルリンク、必要時の `.txt` 形式などを、実際に利用可能と確認できた範囲で案内する。本人に公開共有リンクの取得を不要に求めない。
6. **結果を分けて報告**：`file_generated` / `provider_saved_and_readback` / `link_target_checked` / `recipient_download_confirmed`。ユーザー端末側まで未確認なら「保存先に格納・読戻し確認済み、端末DLは未確認」と表現する。

7. **コピーできる文末表示も用意する**：コピー用の文章ブロックが使える環境では、**短いMarkdown・コード・手順・別AIへの指示**などは、文末に全文をコピーできるブロックを置く。目安は本文4,000文字程度までで、見出し・改行・コード記号を保持する。標準UIにコピー機能がなければプレーンなコードブロック等で代替する。
8. **長い資料を無理に画面へ重複しない**：長文の場合は**取得を確認した実ファイルの個別URL**を主経路とし、文末には短い実行指示・要点・冒頭サンプルなどコピーに意味がある部分だけ置く。**省略版を全文と偽らない**。長文の全文貼付を本人が明示した場合は適切な区切りで全文提示する。
9. **配布先に応じる**：スマートフォン、Web、共有先AIなどで保存・コピー操作が異なる。実端末でのダウンロード成功は**本人の報告**で更新し、コピーブロックの閲覧を端末保存と取り違えない。本人からクラウド経由のDL成功報告があれば、その経路について受取成功と記録し、同じ確認を聞き直さない。

例：ChatGPTアプリの一時ファイルリンクで2件の受取失敗が報告されたら、同一の一時リンクを何度も再掲せず、非公開の既存保存先へ同一本文を保持して個別リンクを提示する。**トークン削減よりも、ユーザーが確実に受け取れることを優先**する。ただし全案件で保存先を二重化する必要はなく、失敗が起きた環境や重要成果物に限定する。

公式ヘルプ：[生成ファイルのダウンロード失敗](https://help.openai.com/ja-jp/articles/7996703)、[ChatGPT Libraryのファイルダウンロード](https://help.openai.com/ja-jp/articles/20001052-using-library-to-manage-files-in-chatgpt)。

## 6.2 人間向け依頼タグとAI間通信（開発・調査の基本）

開発調査、設計、実装、文書・スライド、PR、検証報告などで、**利用者に実際の対応・判断・確認を求める箇所**に次の全角カギ括弧付きタグを可視表示する。対応不要の情報共有には必要に応じて【情報】を使う。AI間の引継ぎだけならタグを形式的に付けない。

|固定タグ（文字列そのまま）|用途|担当|
|---|---|---|
| `【要確認】` | 表示、内容、実際の操作性、意図との一致を利用者が目視確認 | 人間 |
| `【要判断】` | 方針採否・公開・承認・優先度など利用者が意思決定 | 人間 |
| `【要対応】` | 作業や回答などの対応を求める | 人間 |\n| `【情報】` | 対応不要の情報共有 | 情報表示 |\n| `【AI検査】` | ファイル、形式、リンク、内容整合、参照、機密情報等をAIが検査 | AI |
| `【未検証】` | 検査未実施、証拠不十分、環境未確認などを理由とともに明示 | 状態表示 |

### 表示・運用の要件

1. **タグは目視で読めるプレーンな文字列**とし、確認対象の見出し・段落・表のセル・レビュー項目の**先頭**に置く。MarkdownのHTMLコメント、GitHubのソース差分だけ、コード、見えないメタデータ、色やアイコンだけで代用しない。通常の文章内の単なる強調やリンクは確認依頼ではない。
2. レビュー対象には **対象の直接リンクまたは開ける実物、確認する位置・観点、求める回答・判断**をセットで示す。人間には原則としてレンダリング画面（MarkdownならPreview、PowerPointならスライド、Webならプレビュー）を案内し、ソースコードの読解を要求しない。
3. **【要確認】・【要判断】・【要対応】のうち必要な承認が未処理なら、公開・マージ等の承認が必要な操作を完了としない**。確認不要の一般案内やAIだけで完結する処理に、装飾目的でタグを乱発しない。
4. **【AI検査】は担当区分であり、それだけでPASSを意味しない。** 必須品質ゲートは検査方法・証拠・対象版に基づき `PASS` / `FAIL` / `NOT_RUN`（適用外は理由付き `N/A`）を別記する。【未検証】には理由・担当・次の検証を添え、PASSに見せかけない。
5. 人間が確認すべき箇所のマーキングは **レビュー依頼文、Draft版、レビュー用注記**で行う。正式公開する読み物・配布資料には、レビュー専用タグを原則として残さない（正式な業務チェックとしてタグ自体が必要な場合を除く）。
6. 返答は原則として「確認OK」「修正：対象と内容」「採用／保留」といった**普通の言葉**でよい。GitHubのApprove、チェックボックス操作、細かい差分チェックを無条件に要求しない。
7. 複数AI・複数チャットでも同じタグを使う。タグ付きレビュー依頼の合格条件は、**必要箇所に正しい固定文字列がレンダリングされ、対象と人間の次の行動が一目で判別できること**。表示確認ができない端末は `【未検証】` として扱う。

**レビュー依頼の最小例：**

> 【要確認】[導入案内の表示プレビュー](wiki/Home.md) — 初見の人に目的が伝わり、次の操作が見つかるか確認。返答：「確認OK」または「修正：箇所・内容」。
>
> 【要判断】PR公開の可否 — 実装済み／未検証／構想の区別に問題がなければ「公開可」、必要なら「保留」と返答。
>
> 【AI検査】ファイル・参照整合：PASS（対象版と実物の読戻しで確認）。
>
> 【未検証】iPhoneでのリンクの実タップ：NOT_RUN（当該端末の操作未実施。実機表示確認待ち）。

### AI間の引継ぎと推奨の提示

- **AI間通信と明示されている場合**、社交辞令・過度な同意・感情的配慮を省き、結論・根拠・不確実性・問題点・次の行動を率直かつ簡潔に伝える。重要な考察・懸念もコピー可能な引継ぎ本文に含める。人間向けメール等の文体はこの規則で一律に制限しない。
- AI間の引継ぎでは人間向け依頼タグを形式的に強制しない。人間に実際の判断や対応を求める箇所だけ該当タグを使う。
- 利用者への推奨案があり、短い承認だけで進められる場合は、詳細な選択肢を増やさず「**推奨で進めて良ければ、『進めて』と答えてください。**」と簡潔に確認する。ただし、別途必要な権限・明示同意をこの返答だけで代替しない。

## 6.3 AI出力の一貫性と人間への引き渡し（試験運用）

同じ用途の成果物は、既に使っている**表示形式・コピー方法・情報の順序**を原則引き継ぐ。変更するのは、利用者に明確な利益がある場合とし、必要なら変更点と理由を短く示す。目的に応じて表・文書・ファイルを選ぶ自由は妨げない。

**共有・保存する成果物は、それ単体で利用目的を達成できる内容にする。** 判断に必要な分析・所見・懸念・提案・未検証事項・判断依頼を、コピー・共有される資料の**外側に残さない**。「私の所見」等が必要なら資料内の一節に含める。単なる作業実況や雑談の収録は不要。

人間がリーダー・別チャット・別AIに資料を渡す必要がある場合は、既存の通常報告に加え、次の**3項目を同じ順序**でまとめて表示する。資料名は**その資料を直接開けるクリック可能なリンク**にする。以下の `資料の直接URL` は表示時に実URLへ置き換える。

> 【引き渡し】リーダーへ[報告資料名](資料の直接URL)を渡してください。
>
> 【依頼事項】リーダーが判断・実施する内容を1文で示す。
>
> 【確認状況】資料保存：NOT_RUN／リンク先の実体確認：NOT_RUN／受け手の閲覧：NOT_RUN（実測結果に必ず置換し、未保存なら「未保存」と記す）

例示の `NOT_RUN` を含む各判定は実測値へ置換必須とし、未保存は「未保存」、未確認は `NOT_RUN` とする。リンク先が存在することと受け手が実際に閲覧できることは別に確認し、非公開DriveのURLを公開Issueへ載せない。**共有対象の判断材料はすべて資料内**に置き、引き渡し欄の外へ重要情報を付け足さない。表示・コピーの実端末での成功は、確認できた範囲だけ報告する（§6.1、§6.2）。

**参照保存・台帳登録の完了境界（β、引継ぎ用）**：報告・引継ぎで「受け手が取得して次の作業に使うファイル」として挙げる成果物・基準文書は、報告完了の前に**受け手が許可された既存の永続保存先**へ実際に保存し、正しいファイルID／個別リンクで読戻しを検査する。対象KBに既存のregistry・索引がある場合は**その台帳への登録・変更時の版／ハッシュ整合**も完了条件とする。個人KBでGoogle Driveとregistryを使っている場合は、その既存の保存・台帳手順を用いる。別環境へDriveや台帳の新設を強制せず、すでに取得可能な公開原本や外部の根拠文献の再保存も要求しない。**そのAIの一時作業領域だけにあるファイル**を「引継ぎ先で取得できる」と書かない。保存、台帳登録、リンク読戻し、相手側の取得・理解・実適用は**別々に**PASS／FAIL／NOT_RUNで記録する。必要な保存・登録が未完なら**参照引渡しは未完了**と明示し、判断用の報告本文や安全な独立作業は続行してよい。非公開資料を公開先へ移すための権限変更・添付・URL転載は無断で行わない。

**人間による引き渡しが必要な場合は、対応UIで引き渡し文全体を一操作でコピーできるようにする。** 「引き渡し文をコピー」等の操作を設け、**実際に1回の操作でクリップボードに実URL（表示ラベルだけではない）と【引き渡し】【依頼事項】【確認状況】の全文が欠落なく入ったことを確認した場合だけ一操作コピーPASS**とする。非対応UIではコピー可能なテキスト／コードブロックを代替とし、一操作達成は保証しない（UI非対応と実操作 `NOT_RUN` を区別する）。資料本文は不要に再掲しない。追加操作が不要な場合は「利用者の追加操作：なし」と示し、コピーを要求しない。端末差を受容し、ボタンの色・装飾に依存せず、**表示確認と実際のコピー成功は別々に判定**する。

**Windows向け `.ps1` をダウンロード提供する場合**、実行手順に次の案内を必ず添える：「**入手先と内容を確認してから**、ダウンロードした `.ps1` を右クリック →［プロパティ］→［全般］→画面下部の［セキュリティ］欄で［許可する］にチェック →［適用］→［OK］。環境によっては［ブロックの解除］と表示される場合がある。該当項目がなければ、この操作は不要。」これはインターネットから取得したファイルのブロックを解除する操作で、**スクリプトの安全性や実行成功を保証するものではない**。PowerShellの実行ポリシーや管理者権限は別の条件として扱い、組織のポリシーを一律に `Bypass`／`Unrestricted` で回避する案内はしない。

## 6.3.1 β運用：混乱時の作業チェックポイントと速い切戻し（2026-10-23）

**このチャット内β介入にも§0のAD&C全体契約を適用する。** 小さく可逆な変更は、計画・比較試験の完成を待たず、**最小実装→静的検査→限定利用→実例から改善または切戻し**へ進める。新しい規則や大きな仕組みを先に増やさない。効果が未実証なら「β／効果NOT_RUN」と明示する。変更前の版・差分・撤回条件を残し、実測で利用者負担が増えたら削除・復元する。ここでの事前承認簡略化は**低リスク・可逆な範囲だけ**であり、公開先や権限の変更・課金・外部送信・本番破壊・秘密情報の扱いは§4ほかの承認境界を維持する。

**同一チャットでのβ介入（通常時は何もしない）**：同じ修正を2回NGとされた、同じ不採用方式に戻った、または利用者が混乱の整理を求めた場合に限り、AIは**今回の目的／変更不可の条件／現行の採用状態／繰り返さない失敗／次の異なる手段**を数行の作業用チェックポイントとして内部で整理する。必要な元資料と承認状態は再確認するが、長い失敗過程を毎回再掲したり、これだけのために新しいチャットを要求したりしない。本人に必要な判断がなければ、そのまま次の修正を進める。同じ方式の微修正を無限に繰り返さず、実現困難なら理由を示し手法変更・中止を選ぶ。**同一チャットの過去トークンを物理的に消したと主張しない。**

**成功時の緩やかな基準復帰（β）**：会話上の手応え、利用者の賛同、局所的なPASSや成果物の完成に引っ張られ、当初の目的・担当・AD&Cの既存規定を緩めない。一方で、本人が気に入っている話の流れ・表現・有効な工夫はできる限り維持する。**案件の区切り、正式報告・引継ぎ、目的や担当のずれが疑われる時だけ**、適用対象の現行正本を必要箇所だけ照合し、**ずれた部分だけ小さく戻す**。全履歴の再読込・毎回答の定型儀式・会話全体の巻戻しは行わない。特に研究報告は既存T005の契約（観測事実／未検証仮説／改善案最大3件／PASS・FAIL・NOT_RUN／次の判断1件）へ戻し、チャット内の「成功」を実取得・受け手の受領・独立検証などの成功へ昇格させない。明確なずれがなければ何も変更せず継続する。

**担当間の判断理由の受渡し（β）**：重大な採否・差戻し・作業引継ぎで「結論だけでは次担当が誤判断し得る」場合に限り、**既存の** Project Context／BUILD_PLAN／該当Issue／成果物の報告本文に、`対象ID・結論／WHY（上位目的と必要になった理由）／棄却案または反例／適用・停止条件／現行正本への参照` を**最短の数行**で残す。重要所見を引渡し資料の外側に残さない。既存の正本・START_HEREから必要箇所だけをたどり、履歴全件を毎回読み込まない。PRIVATE原本の内容・URL・個人情報は公開Issueへ写さず、公開側は非機密の状態と参照区分だけとする。

**受信・理解・適用を分離（β）**：受信側の担当AIは、取得可能な**当該受渡し原本を実際に開く**→WHYと棄却案・反例を自分の言葉で復元→Issueの現行状態、BUILD_PLAN、対象正本の版・承認と照合→許可範囲の具体作業へ適用する。記録／投稿、実取得、理由復元、現況照合、作業適用は**別々に PASS／FAIL／NOT_RUN（証拠・担当・対象版付き）**を付ける。送信側の投稿・自己読戻しは別担当の受信PASSではない。資料・接続が使えなければ当該ゲートはNOT_RUN、矛盾すれば影響作業を停止し、他の既済成果を保全する。確認のための新DB・自動配送・追加担当・新チャットは作らず、既存Issue #13の案件と通常報告を使う。βの導線が実務を邪魔する場合、§0に従って**この追記だけ**を取り消す。

**試験と停止**：まず旧NGへの回帰・追加の人間修正回数・再説明・余計な表示・労力を自然観測。介入効果や数%の改善は比較前に断定しない。かえって邪魔なら「このβを使わない」という本人の意思をそのチャットで尊重する。Git上のβは変更前版を使った**新しい復元コミット**で切り戻す（履歴を破壊するforce pushは不要）。他チャットの設定・既存のコンテクスト・すでに行われた外部操作はGitの切戻しでは元に戻らない。実配信は各AI/チャットが本節を取得したときだけであり、GitHubへの保存だけで自動適用済みとはしない。

### 作業状態復元と成果物照合のβ実装（PR #31採用・2026-10-25）

**変動入力から処理構成を導出（β）**：実行ツールを作るとき、原稿・ファイル・対象ID・順序・対象件数など通常の運用で変わる値と、承認・品質・API制約など変えてはいけない条件を分ける。入力から対象数と必要工程を計算し、対象0件は無処理、試聴対象が最大3件なら入力が1〜3件のとき後段を起動しない。15件など単一案件の実績値を汎用ツールの必須件数へ昇格しない。0／1／分岐前後／通常件数／不正入力を少数の境界テストで確認し、実用範囲外は明確に停止する。無制限な汎用化や新しい設定層は作らない。

**作業状態の復元を優先（β）**：特定の成果物を修正・再開する場合、既存START_HERE／Project Context／BUILD_PLAN／成果物引継ぎから、対象ID・採用版・必要素材／実行キット・手順・既済検査・今回の変更対象を必要量だけ組み立てる。確定版は無断で再選定せず、明示的な再検討依頼があれば調査経路へ戻る。Drive等のリンク文字列や過去の「保存PASS」だけでは実体の再取得PASSではない。利用可能なコネクタで実体・版・必要なhashを照合し、未取得はNOT_RUN、実体の不一致はFAIL。欠けた参照の補修を先に試み、勝手に代替生成しない。成果物の引継ぎ完成は、保存先・版確定→保存先から読戻し→参照照合の後に判定し、次の独立AIによる実適用は別ゲートとする。全案件へ新しい引継ぎ台帳やロックファイルを強制しない。

**要求と成果物の照合（β）**：上流で確定できる選択・採否・制約を先に確定し、現場担当へ不要な再判断を持ち込まない。制作・納品タスクは、作業開始時に当該正本から「今回必須／任意の成果物ID・種別・条件・判断主体」を復元し、終了時に実成果物をID単位で照合する。形式の選択／両方制作などの採否は対象案件の最新の承認済み正本に従い、AIが勝手に追加・省略しない。未照合の形式は推測で必須化しない。通常検査は実体存在・非空・対象数を軽く確認し、音声・映像デコード／再生・内容品質は別ゲートで判定する。制作終了後に必須物が欠ければその成果物をFAIL、制作未了・取得未実施ならNOT_RUN、他の成果物のPASSで全体完了へ昇格しない。失敗時だけ取得／解釈／実行／検査のどこに問題があるか詳しく調べ、正本の改定履歴や判断理由を先に確認してルールを増やさない。

**機械的β検査の範囲**：`scripts/adnc_resume_preflight.py` は、既存資料からその場で組んだJSONと実取得済みのローカル検査用ファイルを対象に、識別子・SHA-256・件数から段階計画とPASS／FAIL／NOT_RUNを返す**読取専用の参考実装**。Drive等を自動検索・取得するツールではなく、API課金や制作物の書換えも行わない。全チャット自動発動や時間・工数削減の効果は未検証。対象別の実行ツールに組み込むかは実試験の結果を見て判断する。繰返し失敗のトリガーは次の既存規定を再利用する。

## 6.3.2 現場タスクの「1実行正本」と優先適用ポインタ（2026-10-24採用）

**目的**：人間が準備→実行→検収まで一続きの仕事として扱え、AIが現行の説明書を探し分けたり複数の手順書を読み比べたりしなくて済むようにする。ハガキサマリーの「準備面／プレイ面」のように、**現場で行う1タスクにつき、読む現行の実行正本を1ファイルにする**。この原則は作業パッケージの粒度に適用し、KB全体・根拠資料・実コード・素材を1ファイルに詰める意味ではない。

**現場手順書の冒頭に置く適用欄（個人用実行パッケージ）**：

```text
優先適用手順（個人KBの現行正本パス／ID）：未設定
適用規則：ここに参照先が記載されていれば、必ずその手順を使用する。
未設定なら、この文書の標準手順を使用する。
参照先を実取得・版確認できない場合は、推測で別手順へ切り替えず、当該工程を停止して報告する。
```

- 
**変更依頼の実行単位（必須）**：現場の手順書／Runbook／実行型Skillで「変更」を扱う場合、`現行正本と影響参照の特定 → 変更案・差分の説明 → 「変更を実装しますね？」と本人確認 → 承認された最終正本への反映（必要な台帳・Git・実行設定等を含む）→ 読戻し・実物検収 → 完了／未完了報告`を、その現場の既存工程に含める。新しい並行手順書や管理表を増やさず、必要な箇所だけ適用する。対象外・未承認・取得不能・書込不能な工程は`BLOCKED / NOT_RUN`等で明記し、実際の変更を伴わないDraft／PR／報告だけを完了にしない。

**1タスクの完結性**：実行正本に目的・適用条件／対象外・必要入力・準備・実行順序・必須出力・検収方法・停止条件・次工程への引渡しを含める。コードや素材は別の実体として保持し、正本から実ID・現行版・参照先を直接解決する。確定済みの判断を現場で選び直させない。
### 付属資料・素材・実行ツールの入口と束ね方（2026-10-25／β採用）

**配置を固定**：現場で使用する手順書／Runbookは、冒頭の「優先適用手順」欄と目的・適用条件の**直後、実行工程より前**に、必ず**「必要資料・素材・ツール」**を**1か所**置く。必要物がない案件は`該当なし`と記す。タスク別にこの場所を探し直させない。資料の原本・コード・実素材は既存の保存先に置き、この欄は**取得入口**とする。別の並行正本・新しい全件台帳を作らず、既存registry／Asset Record／Project Context／原本リンクを参照する。共有手順書には非公開fileIdや本人情報を書かない。

**1件ごとの最小欄**：`素材ID（既存ID）｜種類（画像・音声・動画・書類・コード／ツール・設定）｜役割／使う工程｜必須・条件付き必須・任意・禁止｜採用状態（正式／候補／旧版等）｜現行版／実取得先｜期待件数｜確認状態`。少なくとも**必須物**はID・実ファイル取得先・採用状態・使用工程・件数・検収方法が一意に解決できること。該当なしを除き、リンクだけ・フォルダ名だけ・過去チャットの画像表示だけで「取得済み」としない。既存資料から一意に復元できる詳細は二重転記せず**同じ欄内でその直接参照**だけを示す。元資料と違う採用判断を創作しない。

**画像が複数ある場合**：同じ仕事で**比較・選択・配置判断が必要な画像**が2枚以上あるときは、見落としを防ぐ**単一の視覚一覧**（番号・素材ID・正式／候補を表示したコンタクトシート等）を原則用意し、上記の入口欄から直接参照できるようにする。多数なら**1つの複数ページPDFなど**でよく、判読不能な小画像を1枚へ詰め込まない。**一覧画像は閲覧補助であり、元の画像の代替原本ではない。** 解像度・透過・編集可能性・個別採用の判断には元画像を取得する。動画コマや設計図等に既存の同等一覧があれば再生成しない。取得できない画像がある場合は不足IDと件数を`NOT_RUN`で残し、一覧にないものを「存在しない」と断定しない。

**ツール・複数ファイル構成**：ツールを動かすには、実行入口、使用OS／環境、実コード・必要な設定や素材の参照、同梱物の期待一覧・必要版・依存条件・検査方法を同じ入口欄から解決する。複数ファイルが一緒に動くツールは、既存の正式なZIP／リポジトリ／実行キット等**1つの取得入口**を優先し、必要な場合のみ内部のファイル一覧と配置関係を短く示す。ZIP化・新ツール開発を無条件に義務化しない。秘密キーは一覧へ記載せず、§6.4の管理保管庫と設定手順を参照する。

**人が起動するツールのゲームニクス（β・2026-10-27）**：内部のファイル構成よりも、初めて受け取った人が **「何を実行する → 何が起こる → 結果はどこ」** を迷わずたどれる操作導線を優先する。実行キットを配布する場合、人間向けの**起動入口は原則1つ**（Windowsなら `START.cmd` 等）とし、補助スクリプト・設定・依存物は `internal` 等へまとめる。入力場所と結果の取得先（`RESULTS` 等）を短い案内と実行画面から一意に確認でき、進捗・失敗理由・次の操作が分かるようにする。複数工程は入口から順序を案内／安全に自動化し、利用者に内部ファイルの探索や確定済みの再選択をさせない。APIキーの初回登録・安全な自動再利用は§6.4に従い、毎回の手入力を既定としない。**単一コマンドのCLI、AI内部だけのツール、既存の使いやすい製品UI**には余計なランチャー・ZIP・独自画面を増やさない。必要な本人承認と安全停止は維持する。

**実行前・完了時の照合**：作業開始時に必要な素材IDの集合と期待件数を、**実際に取得できた原本／ツール／一覧内ID**に突合する。取得成功と一覧の見た目だけの確認を分ける。採用版・必須物・使用許可に矛盾があれば、影響工程を止めて既存T015方式で未完了に残す。実行後は`必要ID → 使用工程 → 成果物上の実確認 → PASS/FAIL/NOT_RUN`を確認する。画像一覧の作成・表示だけを個々の素材の取得PASSや成果物完成Q4とみなさない。**新規・重大改訂ではQ2コールドスタート時に「全件に到達できたか」を独立に試験**し、軽微改訂は変更した素材群だけ確認する。

- **分ける判断**：1つの実行正本で流れが完結しない場合、説明書を並列に読ませるのではなく、独立して完了・検収できるタスクへ分け、各タスクに1つの現行実行正本を持たせる。長大な文書への機械的統合をしない。
- **個別手順の作成と優先**：本人から別方式・変更を求められたら、適用対象の**個人KBに独立して実行可能な手順書**を作成／更新し、利用する現場パッケージの冒頭欄にその**実在する正本パス／ID**を記載する。欄に値があればその個別手順を適用し、なければ標準を使用。あいまいな複数候補・循環参照は解消してから運用する。
- **プライバシーと版**：共有KBや公開テンプレートには個人KBの非公開パス・ファイルIDを記入しない。個別の優先参照は非公開の利用者側パッケージにのみ置く。既存の標準・コード・原本の正本関係と権限は保ち、旧版は既存履歴へ。
- **手順作成時の確認**：冒頭の優先参照の有無、指定先の実取得・版／ID、単体での作業完結性、必要コード／素材の到達、必須出力の照合を確認する。見つかっただけ、リンクがあるだけでは復元・実行PASSにしない。初見AIが1行指示から適切な1実行正本へ到達できるかを既存T005／T010で実測する。無関係な新索引・ジョブ・管理層は作らない。

### 案件固有の確定条件と一般標準の順序（2026-10-25／暫定採用）

**既存案件の再開時**は、(1) 今回の本人指示 → (2) 実取得した案件固有の**採用済み条件**と現行作業状態 → (3) 未決定部分に限る一般標準 → (4) 低リスクで可逆なAI裁量、の順で具体化する。過去に同じ素材・手法を使った**履歴だけ**では、現在の採用条件・今回の課金や公開承認とみなさない。案件固有の採用記録が取得不能なら、その適用範囲を`NOT_RUN`とし、一般標準に勝手に上書きして「同じ案件を再開できた」とは報告しない。既存の1タスク1実行正本／Project Context／BUILD_PLANに採用条件・必須成果物・実体参照・未完了工程を置き、新たな並行台帳は作らない。

**再開地点は案件ごとの現行位置と追記の歴史を区別**する。旧履歴中の「再開位置」が複数あるだけで不整合と断定しない。現在の採用地点が複数あって競合するときは、上書きで統一せず影響する案件だけ保留する。次回AIへの引渡しは「今回の目的／案件正本／採用済み条件／再開地点／取得不能な資料／未実施ゲート」の短い記録を**既存**の計画・成果物へ残す。

### 更新直前の基準照合と書込後検収（2026-10-25／暫定採用）

同一KBを複数担当AIが扱う場合、変更対象のDrive fileId・現行本文のSHA-256・可能ならDriveのversion・台帳の対象revision/hashを**実取得した基準**にする。保存直前に対象原本と関係する台帳を再取得し、基準から変わっていたら対象だけ保留し、独立な差分でも自動統合が安全か判定する。承認済み差分が実保存できたら、変更した実体と該当台帳を**実再取得して整合検査**し、それまで採用済みの完了とは表現しない。取得失敗は内容不一致のFAILと区別してNOT_RUNにする。

この**再取得・比較は楽観的な競合検知**であり、Google Drive上のサーバー側CAS、複数ファイルの原子性、検査後から書込前の競合（TOCTOU）防止は証明していない。現行Drive API／使える接続が条件付き更新を正式に保証できない限り、同一KBの本番**確定書込は1担当に集約**し、他担当AIは候補作成・読取検査とする。相手AIの更新を勝手に巻き戻さない。失敗時の変更前版・ID・理由は既存履歴／BUILD_PLANに残し、復旧そのものを新しい変更として再検証する。

**検査の適用範囲**：変更のたびに触った実体と参照だけ安く調べ、全件ハッシュ・孤立参照等は実行環境・承認がそろう定期点検／障害時へ分離。検査が可能なら[KB整合検査器（読取専用β、利用環境での実行は別検収）](../scripts/check_kb.py)相当の実行可能な処理で実施するが、未採用コードやPython未対応環境では「自動検査PASS」と偽らない。検査器のPASSは意味的な再開成功ではない。

## 6.3.3 実行指示書の品質基準（2026-10-25・v0.1 β採用）

**合格条件**：初めて担当する能力のあるAI／人間が、過去の会話・暗黙の了解に頼らず、当該タスクの**意図された完成品を制作・検収し、必要なときだけ人間に引き渡せる**こと。
**変更依頼に対する必須出口**：変更を含む実行指示書には、「最終実装の対象（正本・派生参照・適用先）」と「保存／Git反映／読戻し／必要な実動作確認」の終了条件を指定する。すべてを実施できない場合、完了宣言ではなく、未完了の対象・理由・次の担当／工程を既存の追跡記録に残す。独立評価や人間による最終採否をAIの静的PASSで代替しない。
§6.3.2の「1タスク・1実行正本」に適用する。**作業手順に従えたことと、利用目的に合う完成品ができたことは別**。創作物の採否・ユーザーの好みなど客観基準だけで確定できない部分は、最終的な本人判断を残し、AIの自己採点で完成としない。

**人が起動するツールの導線検収（β）**：実物の配布形態を前提に、初見の利用者が入口を見つけ、必要な初回設定だけで起動し、入力・進捗・結果の場所・失敗時の再開方法に到達できるかを検査する。既存設定の再入力や内部スクリプトの選択を要求した場合は改善対象。**構造・案内の静的検査と、対象OSでの実行・結果取得は別ゲート**とし、実機未確認は `NOT_RUN`。毎回の確認画面や新しい検査帳票は作らず、§6.3.3の既存Q1〜Q4へ必要な結果だけ記録する。

**作成時の確認観点（10項目。10節の新設や毎回10件の入力を強制しない）**：①目的と成功条件、②適用範囲・実行単位、③入力・現行正本と競合時優先順位、④完成品の内容・形式・許容品質、⑤最小標準手順、⑥分岐・欠落・禁止代替、⑦権限とAI／人間の担当境界、⑧実物による検収と証拠、⑨保存先・相手が開ける受渡し、⑩変更・停止・再開条件。既存の正本／標準から一意に取得できる内容は**参照だけ**でよい。適用外は理由付きで `N/A`。旧版全文・操作のクリック手順・過去の経緯を無闇に転記しない。

**必須要件の端から端までの接続**：完成品の**必須**条件ごとに `完成要件 → 使用する現行素材・正本（ID／版／実取得先）→ 実行工程 → 検収方法・証拠` が解決できなければ、指示書の記述品質 `Q1` は未達。既存の本文・検収欄に記載されていれば重複表を作らない。「正式ロゴを使用」だけでは不十分で、実ロゴの識別・取得、配置、出力実フレームでの確認と取得不能時の停止までが必要。**正本にない素材IDや許諾を推測で補完しない**。

**指示の強さと競合**：`必須`／`条件付き必須`／`原則・目標`／`任意`／`禁止` を、結果が変わる箇所で明確にする。数値目標と内容品質が衝突するときの優先順位を定義し、尺・ページ数などを満たすためだけの水増しをしない。記述を増やす判断基準は「**未記載なら結果・必要な判断・失敗検出・安全／権限・費用の境界が変わるか**」。変わらなければ記載を増やさない。

**現行手順書すべての冒頭に置く短い改訂注意書き**（タイトル・メタデータの直後、実行本文より前。共通品質基準を全文複写しない）：

> **修正時の必須参照**：この手順書を修正する前に、[AD&C共通実行標準 §6.3.2〜§6.3.3](https://github.com/Yosio-DMZ-C/AI-DODAI-Continuity/blob/main/docs/PROJECT_EXECUTION_STANDARD.md)の現行本文を**実取得**し、その品質基準に従うこと。軽微な修正は影響箇所だけ再検査する。
> **変更依頼時の完了基準**：「変更して」は実装済み正本を求める依頼。対象を確認し、書込直前に「変更を実装しますね？」と承認を得る。承認後は正本・必要参照と台帳・Git等へ実反映し、読戻す。Draftや提案だけなら未完了として明示する（同標準 §6.3.2〜§6.3.3）。

この1文は、個人KB・共有KB・その他の**現行の実務手順書／Runbook／実行型Skill**の新規作成・重要改訂時に必ず付け、既存の現行手順書へのバックフィルも行う。**日常の実行・参照時には品質基準の追加取得を強制しない**。保存済みの**旧版・歴史的原本・索引・資料**は改訂対象にしない。既存手順書の本文変更によって台帳に登録されたチェックサム・版・履歴が不整合にならないよう、対象の実取得→バックアップ→本文の局所変更→登録情報（必要に応じてrevision/hash等）の更新→再取得・照合を**既存の更新手順**で行う。ヘッダーの存在と、改訂時に基準を実取得・適用した事実は別々に判定する。

**品質判定は4つを混同しない**：

| 判定 | 実際の合格条件 |
|---|---|
| `Q1 記述品質` | 必須の要件→工程→検収の接続、正本・参照の一意性、矛盾・重大な欠落なし |
| `Q2 実行解釈` | 作成者とは別の担当AI等が、実行単位・優先順位・停止条件を正しく復元 |
| `Q3 実作業` | 対象の実環境で必要な作業と実体検査を完了。模擬・部分試験の範囲を明示 |
| `Q4 成果物品質` | 完成品が用途・必須条件を満たし、必要な本人／利用者の採否確認も終えている |

**β導入と独立試験の負担制御**：新規採用・重大改訂時は、少なくとも独立担当のコールドスタート `Q2` と、該当業務に固有の正常・誤単位・旧版混入・素材欠落・権限境界などの**重要な失敗条件**を検査する。必須要件にかかわる実制作の `Q3/Q4` は実物でのみPASS。未実施は `NOT_RUN` のまま、β試作・低リスク差分作業を進めてよいが、「品質基準合格」「完成」と表示しない。軽微改訂では影響範囲だけ再検査し、毎回別AI起動や全項目試験を義務化しない。検査結果とWHYは既存Runbook・QA・Project Context・Issueへ最小記録し、新たな台帳・DB・審査層を作らない。負担が増す場合は§0の小差分切戻しを適用。

## 6.4 APIキー・秘密情報を扱う外部連携ツールの契約

プラグイン、MCP、外部API、PowerShell／CLI、定期処理を作るときは、認証情報の保存・再利用・失効方法を**成果物と同時に説明**する。具体的な保存先・操作方法・例・制約は[APIキー・秘密情報の保管と再利用](API_SECRET_HANDLING.md)を正とする。

1. **毎回入力させない**：公式OAuth／OIDC／接続先の管理保管庫を優先。APIキーが必要なら初回設定・更新時に安全に登録し、通常の実行時は自動読込。毎回の手入力を既定の運用としない。
2. **実行環境に適した保存方式を必ず明記**：WindowsユーザーのPowerShellはDPAPIによるユーザー別暗号化ファイルを初期候補とする。別アカウントで動く無人処理は組織Vault／承認された秘密情報保管先、GitHub ActionsはOIDC／Actions Secrets、WorkersはWorkers Secretsを使用する。環境別の利用可否を実際に確かめる。
3. **秘密値は利用者のKB・チャット・ソース・Git・ログ・コマンド引数に載せない**。暗号化ファイルの保存先パスや保管庫名は説明してよいが、値は掲載しない。平文の永続環境変数を標準方式にしない。
4. **提供時の必須案内**：認証方式、保存先（値なし）、初回登録、2回目以降の自動読込、実行アカウント、定期実行可否、更新・失効・端末移行、障害時停止、PASS/FAIL/NOT_RUNを示す。「環境変数に入れる」だけでは説明完了としない。
5. **検証と安全停止**：ダミーキーで登録・再利用・未登録時停止を確認し、必要なら実サービスの疎通は別ゲート。キーが読めないときは説明付きで停止し、毎回入力方式に黙って切り替えない。
