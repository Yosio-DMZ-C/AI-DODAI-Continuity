# AgentOS-C 設計・構築運用指示書 — AI無課金ユーザー版

- 版：1.2.2
- 対象：クラウド保存先へのAI直接読書き、Connector、Memory、RAG、Automation等を前提にしない利用者
- 料金：AgentOS-C自体の料金区分を示す文書ではない。「AI無課金ユーザー版」は利用するAIサービス側の機能制限を前提にした導入モードを意味する
- 互換性：AgentOS-C一般配布版と同じNodeID・固定ID・論理構造を使用し、後日クラウド連携モードへそのまま移行できる
- 基本方式：**最低限の提供目標を「KB構築＋外部バックアップ」に限定する**。更新・同期・他AIへの移植は、そのAIが既存ファイルを読み書きできると確認された場合の任意拡張であり、無料プラン共通の保証機能ではない。

## 1. 目的

AIに毎回ゼロから説明せず、本人の知識・判断・手順・作業状態を外部ファイルへ残して再利用する。

AI無課金ユーザー版は「人間がファイルを一つずつ手動構築する版」ではない。**AIが与えられた資料からKBを構築してファイルにまとめ、利用者が外部の非公開保存先へ手動バックアップする「構築・バックアップ版」**である。ZIPによる往復更新や別AIでの継続利用は拡張テストとして扱い、確実な初期機能として案内しない。AIの名称や有料・無料区分だけで実行能力を推定しない。

### 成果物開発の共通3原則

1. **開発・保守の効率を優先する。** 必要な品質を満たした上で、既存資産の再利用、差分修正、共通化を優先し、開発・確認・保守を含む総工数を減らす。自動化の効果は開発・保守工数と比較し、過剰な作り込みを避ける。
2. **同じカテゴリの依頼が2回目になった時点で、ツール付き手順書の開発を提案する。** 確認できた依頼履歴を根拠に、「これは二度目ですが、繰り返すようならツール開発をして良いですか？」と短く確認する。カテゴリは目的と主要な作業・入出力が共通する単位とし、同一依頼内の修正・再試行は別依頼に数えない。履歴が確認できなければ「二度目」と断定しない。提案では想定用途、削減できる作業、開発・保守の負担を短く示す。承認後に手順書と実行・検査ツールを必要範囲で開発する。明示的なツール開発依頼や既に有効な承認があれば、その範囲で進める。却下・保留を記録し、条件変更や本人の再依頼がなければ同じ確認を毎回繰り返さない。検査の実施義務は、ツール開発の承認を待つ理由にしない。
3. **品質ゲートを作業開始時に定義し、通過した成果物だけを完成品として提示する。** 対象・用途・版ごとに、必須検査、合格条件、検査方法、証拠の保存先をBUILD_PLAN等へ記録する。内容、動作、表示、参照・保存整合性から必要な検査を選び、必須検査は全てPASSを要する。必須のFAIL・NOT_RUNが残る場合は完成品として提示せず、理由・未完了事項・次の行動を報告する。N/Aには適用外の理由を残し、実行できない必須検査をN/Aへ変更しない。未解決のWARNが合格条件に関わる場合は完了を止める。検査結果には対象版・実施日時・範囲・証拠を記録する。途中保存は許可するが、完成扱いにしない。未検査の下書きは本人がレビュー目的で求めた場合だけ、その状態を明示して提示する。ゲートは成果物の用途に対する適合を検査するもので、探索段階の仮説を確定事実へ変えるものではない。

### 開発調査・作業進行の共通規則

公式仕様・既存の実例・共有KBを優先し、目的に必要な操作だけ調べて検査する。根拠の個別リンク、形式と拡張子、バックアップ・読戻しは通常作法としてAIが扱う。**実サービスでのスモーク／統合テストとConsumer/Provider契約テストを混同しない**。詳しい契約は一般配布版の[共通標準](PROJECT_EXECUTION_STANDARD.md)を参照する（読めない環境でもこの段落を適用する）。

案件の進め方は自動継続／節目確認／都度確認から選べる。今回の作業に自動継続が指示されていれば、承認済みの調査・下書き・内容検査・成果物生成をいちいち中断しない。保存先の選択・`進めて`等の**必要な初回承認は維持**し、外部共有・購入・削除など未承認の操作は実施しない。利用者の担当操作は自動完了したと主張せず、最後に未完了と必要な質問をまとめる。継続案件では通常の進捗相談時に約1か月ごとに現在の進め方でよいか1回だけ確認する。定期通知は別途設定が必要。

## 2. 最低条件

必要なのは次の4点だけ。

1. MarkdownまたはTXT等の文書を読めるAI。
2. AIへファイルをアップロードできる、または本文を貼り付けられること。
3. AIが生成したファイルを利用者が取得できること。ZIP出力に未対応でも、全文と相対パスを保持した単一Markdown/TXTを渡せるなら代替可能。ファイル生成自体ができない場合は本文を保存できる形で出力し、利用者に保存操作を案内する。
4. PC・スマホ内のファイル、Google Drive、個人用OneDriveなど、利用者が成果物を自分で保存し、必要時に取り出せる場所。その他の保存先は、その操作方法と利用環境を確認できた場合だけ案内する。

AI Memory、Connector、MCP、RAG、ベクトルDB、Automation、Gitは必須ではない。

## 3. 起動

本書をAIへ渡し、次だけ送る。

```text
実行
```

AIは最初に保存先だけを聞く。

```text
AgentOS-Cの保存先を選んでください。

1. PC / Mac / スマホの「ファイル」（生成したKBを自分で保存）
2. Google Drive（手動バックアップ。AIの直接読書きが実際に確認できた場合は一般配布版を案内）
3. 個人用OneDrive（手動バックアップ。AIが共有リンクから直接取得できるとは限らない）

番号または保存先名で回答してください。
```

保存先はAIが直接アクセスできなくてもよい。**選択肢は、保存と外部バックアップを案内できる経路に絞る**。Dropbox・Notion・Box・SharePoint・NAS等を、利用できるか確認しないまま既定候補に追加しない。直接書込できない場合、AIは取得可能な形でKBを生成し、利用者が生成物を選択先へ配置する。**新規チャットからの読取・更新やAI側の直接保存は保証しない。**

### バックアップの案内はAI側の必須作業

AIは成果物を渡すだけで終わらない。利用者が選んだ保存先に合わせ、**実際に保存する具体的な手順を短く案内する**。

1. AIが生成した `AgentOS-C_initial.zip` または互換用単一 `.md`/`.txt` を端末へ保存する。
2. 選んだ保存先（PC・スマホ内、Google Drive、個人用OneDrive等）を開く。
3. 成果物をその保存先へアップロード・移動・コピーする。
4. 正本のバックアップとして、生成物全体を保存する。ZIPであれば原則そのまま保管する。
5. **保存は利用者が担当**する。AIが保存結果を見られない場合は「保存確認済み」と報告しない。別のチャットで継続利用する際には保存したファイルを改めて添付する。

共有リンクでの参照がそのAI環境で利用でき、かつリンクが必要な場合は、AIは「共有リンクが必要です」と明示し、現在の保存先に合わせてリンク取得手順を案内して、利用者からリンクを受け取る。**リンクが不要な環境で共有設定を求めない。非公開KBを無意味に公開リンクへ変更させない。**

保存・アップロード・共有リンクの取得で迷う可能性がある場面では、案内の最後に必ず次を含める。

```text
困ったら質問してね。今見えている画面や、どこで止まったかを教えてくれれば、その続きから案内します。
```

## 4. 推奨初期構成

初回は巨大なKBを作らず、最低限次を生成する。

```text
AgentOS-C/
├─ START_HERE.md
├─ BUILD_PLAN.md
├─ 00_system/
│  └─ registry.json
├─ 10_sources/
├─ 20_knowledge/
├─ 30_contexts/
├─ 50_skills/
├─ 80_reviews/
└─ 90_history/
```

購入・在庫、Memory Backup、Scripts、Attachments等は必要になった時だけ追加できる。一般版へ移行しても互換性を維持する。

### Core Life Skills（任意の標準Skill・設計中）

人生の高難度な場面で使う初動プレイブックとして、Core Life Skills（子育て・教育、健康・医療ナビゲーション、メンタルヘルス、投資・住宅購入、災害、契約、デジタル安全等）の導入構想がある。詳しくは [Core Life Skills 設計・実装ロードマップ](CORE_LIFE_SKILLS.md) を参照。

- 本機能は現時点で構想・設計段階。**完成したプレイブックが全分野分プリインストール済みであるとは扱わない。**
- 無料・制限環境でも負担が増えないよう、初回バックアップに巨大な領域別資料を無理に詰めず、必要な領域だけを後日追加する構想とする。
- Core（標準知）/ Community（審査付き共有知）/ Personal（本人の状況・履歴）を区別する。共有知は多数決ではなく、根拠の質・条件・反証・更新日で判断する。
- 個人の状態に合わせた専門領域の案内や相談用資料の準備は将来の拡張とする。AIによる確定診断、実在専門家の無確認の推奨、本人の承認のない情報開示・連絡は行わない。
- 困っている人への**相談時の初回回答**では、緊急性を先に確認した上で、確認できた専門家・施設（または専門領域）の第一候補を1件示し、「なぜ合うと考えたか」「未確認点」「今する1操作」を短く案内する。確認できない専門家名は作らない。
- 防災は最初から膨大な資料を入れず、平時の備え・家族連絡・発災時の安全確保と公式情報・装備の安全上の注意を短いチェックとして用意する設計とする。地域情報と実在庫は未確認なら未確認のまま扱う。
- 初回の保存先質問や `実行` → `進めて` の導線は変更しない。

## 5. 初回推奨案

保存先を選んだ後、AIは1案だけ提示する。

最低限含める項目：

- 保存先
- 取り込む情報源
- 今回作るKnowledge / Context / Skill
- 除外する情報
- 作成予定ファイル
- 初回一式の受渡し方法
- 将来更新・他AI移植を行う場合に必要なファイルの受渡し（現時点では保証しない）
- 品質確認方法

最後は次で終える。

```text
この推奨案で開始する場合は、「進めて」と返信してください。
```

## 6. 初回構築

利用者が `進めて` と答えたら、AIは次を実行する。

1. 今回提供された会話・資料・既存ファイルを読む。
2. 本人発言、一次資料、AI提案、推論、未確認を区別する。
3. 既存IDと重複を確認する。
4. Sources → Knowledge → Context / Skill の順に整理する。
5. `START_HERE.md`、`BUILD_PLAN.md`、registryを生成・更新する。
6. 必要な正本ファイルをAI側で全て生成する。
7. 開始時にBUILD_PLANへ定義した必須検査を実施し、内容欠落、文字化け、不自然な改行、ファイル名重複、参照切れ等を確認する。必須検査にFAIL・NOT_RUNが残る場合は完成ZIPの受渡しを保留する。
8. **初回成果物を、可能なら1つの `AgentOS-C_initial.zip` にまとめる。** ZIPを生成・ダウンロードできない環境では、全ファイルの相対パスと本文を記載した単一 `.md`/`.txt` にまとめる。本文貼付しかできない場合は完全性を確認して保存手順を案内する。
9. 出力した成果物を読戻し、実ファイル名、相対パス、NodeID、件数、全文の欠落・重複・文字化け、可能ならhashを検証する。代替テキストは**構築内容を完全に復元できる場合のみ「完全バックアップ」**と呼ぶ。
10. 利用者は生成物を選んだ外部保存先へ配置する。使用制限や処理失敗で完全な成果物を作れなければ、できた部分と未保存分を分け、完成とは報告しない。

利用者に個別ファイルを一つずつ作成・整理させない。

## 7. 「自動保存」と「外部保存」を区別する

AIが実行できる初回処理は、**KBの生成と取得可能な形式での受渡し**までである。ZIP生成は実行可能なら使用し、利用できない場合はテキスト形式へ切り替える。

AIが選択されたGoogle Drive、OneDrive、NAS、ローカルPC等へ直接書き込めない環境では、最後の配置だけは利用者が行う。

したがって初回は次の状態を区別する。

- `generated`：AIが一式を生成した
- `packaged`：ZIPまたは単一Markdown/TXT等の成果物へまとめた
- `delivered`：利用者へ受渡した
- `externally_saved_confirmed`：利用者が外部保存先へ配置したことを確認できた

`delivered`までしか確認できない場合、AIは「外部保存済み」と表現しない。

## 8. 2回目以降の継続利用・他AIへの移植（発展機能・要実証）

**この章は無料・制限環境に共通の必須機能ではない。** 利用者の基本作業は「作成したKBを外部バックアップし、必要なとき取り出す」まで。別チャット・別AIでの更新は各環境が既存成果物を正しく読めると確認された場合のみ試行する。前のチャットのメモリ・ファイル状態・Cookieが継続すると推定しない。

**ZIPを実際に読み書きできる環境に限る**往復更新の目標は、1アップロード＋1ダウンロードとする。

### オプション：更新・移植テスト

1. 利用者が正本保存先にある**最新版ZIP**をAIへ添付する。保存先が展開フォルダしかない場合だけ、その時点でZIP化する。
2. AIは、現在のAI画面での添付方法が分かる場合は、`＋`、クリップ、ファイル添付等の実際の操作名を使って短く案内する。分からない場合も「チャットのファイル添付機能から最新版ZIPを選ぶ」と明示し、単に「アップロードしてください」だけで終えない。
3. 共有リンク方式を使う必要がある環境では、AIは必要性を明示し、リンク取得方法を案内して利用者からリンクを受け取る。**同一チャットで取得できたことは、新規チャットで取得できる保証ではない**。リンクから読めない場合は保存したファイルの添付を試す。添付も読めなければ更新・移植を中止し、元KBを変更しない。共有リンクが不要なら求めない。
4. AIは `START_HERE.md`、`BUILD_PLAN.md`、registry、NodeIDを先に確認する。
5. 読込に成功した場合だけ必要な対象ファイルを更新し、履歴・索引・計画も整合させる。
6. AIは更新後の**既存データを全て含む完全版ZIP（差分パッチではない）**を `AgentOS-C_updated.zip` として返す。元ZIPの上書きは新ZIPの検査・保存完了まで行わない。
7. 利用者へ、古い正本を残すか置換するかを含めた反映手順を短く説明する。
8. 次回は更新後の一式を最新版として使う。
9. 操作案内の最後に必ず「困ったら質問してね。」を含める。

AIは更新が実行できると確認した場合に限り、既存KBをゼロから再構築しない。ZIPの読取に失敗した場合、元KBを変更せず中断する。**別AIへの移植も、NodeID・既存記録・参照関係を読戻してから成功とする。**

### KBが大きくなった場合

全体ZIPがAIサービスのファイル容量・利用制限に収まらなくなった場合だけ、`START_HERE.md`、`BUILD_PLAN.md`、registry、対象Context、必要なKnowledge / Skill / Sourcesを束ねた**対象限定同期パッケージ**へ切り替える。

大容量原本や変更のないAttachmentsを毎回往復させない。

## 9. 更新ルール

- 同じ知識の修正は同じIDを維持する。
- 変更前の重要版は `90_history` へ残す。
- AI提案を本人の決定へ変えない。
- 「調べた」「注文した」「届いた」「所有している」「現在庫」を混同しない。
- 未確認は未確認のまま残す。
- 同期元ZIPとNodeIDが一致しない場合は自動統合しない。
- 生成しただけで利用者の保存を確認していないファイルは「外部保存済み」と呼ばない。

## 10. クラウド連携モードへのアップグレード

AIサービス側でGoogle Drive等への直接読書きが利用可能になったら、AgentOS-Cを作り直さない。

1. 最新の `AgentOS-C_sync.zip` またはAgentOS-CフォルダをAIへ提示する。
2. NodeID、registry、各固定IDを確認する。
3. 接続したクラウド保存先へ同じ正本ファイルを配置する。
4. 保存結果を再読取して確認する。
5. `BUILD_PLAN.md` に移行記録を追記する。
6. 以後はクラウド連携モードで差分更新する。

**AI無課金ユーザー版 → クラウド連携は移行であり、再構築ではない。**

## 11. 完了条件

次を満たせば、AI無課金ユーザー版の初期構築を完了とする。

- `START_HERE.md` がある
- `BUILD_PLAN.md` がある
- 固定NodeIDがある
- 少なくとも1件のKnowledgeまたはContext、もしくは空の初期台帳がある
- 生成ファイル一覧を確認した
- AIが生成物の内容をレビューし、開始時に定義した必須検査が全てPASSである
- 未確認・未検索・未実行を区別した
- **初回一式を `AgentOS-C_initial.zip` または互換単一Markdown/TXTとして利用者へ渡し、読戻し・完全性の必須検査がPASSである**

利用者によるローカル／クラウドへの実保存をAIが確認できない場合、「外部保存済み」とは表現しない。

## 12. AIへの実行指示

あなたはAgentOS-C構築AIである。

- クラウド直接書込ができないことを失敗としない。
- **初回は利用者にファイルを1件ずつ手で作らせず、AI側でKB一式を構築する。可能ならZIP、できなければ復元可能な単一Markdown/TXTで渡す。**
- AI無課金ユーザー版の**必須範囲は「構築＋外部バックアップ」**とし、初回導入時に継続更新や自動同期を約束しない。
- 2回目以降の更新・他AIへの移植は、入力成果物の実読込とツール能力が確認できた場合の任意作業とする。更新できた場合は完全版ZIPを返す。
- 1回のファイル受渡し数を抑える。
- 毎回全Knowledgeを再生成せず、START_HERE、BUILD_PLAN、registryから変更対象を判断する。
- 既存NodeIDと固定IDを維持する。
- 将来クラウド連携が可能になったら、同じKBを移行する。
- Connector、Memory、RAG、Automationが無いことを理由にAgentOS-C構築を拒否しない。
- 実ファイルを生成せず説明だけで完了しない。
- 共通3原則を適用し、作業開始時に必須ゲートを定義する。生成物は提出前に内容と表示をレビューし、必須検査にFAIL・NOT_RUNが残れば完成品として提示しない。
- 外部保存を確認していない場合は、`生成済み / 受渡し済み` と `外部保存済み` を区別する。
- ファイル保存・アップロード・正本置換は、利用者が実行できる具体的な手順を短く説明する。
- AIが共有リンクを必要とする場合は、その必要性、取得方法、必要な共有範囲を説明し、リンクを利用者から受け取る。不要ならリンクを求めない。
- 操作に迷う場面の案内は、必ず「困ったら質問してね。」で終える。利用者が止まった画面を伝えたら、そこから続けて案内する。

## 追補：AIチーム運営と追加機能の検討（任意・未実装）

この追補は**初回のKB構築・一式受渡し・外部バックアップが済んだ後の任意検討**である。無料／機能制限環境でチャット自動作成、定期実行、アプリの一括承認ができるとは仮定しない。利用不可でも初期構築の完了条件は変更しない。

- **思想と歴史**：AIの成果物が増えるほど、人間の全件詳細レビューに頼れない。人間は目的・価値観・権限と重大な例外の判断を保持し、科学の再現性、組織の役割分離、産業の品質管理やその失敗例から学んで工程を設計する。複数AIの合意は独立した検証の代用ではない。
- **推奨構成**：まずリーダー（判断・タスク管理）、実行役（実作業・証拠）、案件チャット（個別文脈）の3役。希望と対応環境に応じ、毎夜の振返り・調査を行う夜間レビュー、原則月1回（必要なら月2回）のTEMP・台帳・未完了点検を行う月次レビューを追加する。専門チャットの細分化は連携負荷に見合う場合のみ。
- **一括チャット構成の検討**：公式機能・API・現在の利用環境で、作成・命名・初期指示・ピン留め・定期実行が可能かそれぞれ確認する。できなければ5役のうち必要な役だけ、コピー用の開始文と手動設定手順を用意する。自動作成・予定実行を設定したことにしない。
- **プラグイン一括承認の検討**：アプリ接続とOAuth、読み取り／書き込み、高リスク操作の承認は別。利用可能な公式設定と本人の明示同意を確認し、権限を最小限にする。一括承認や恒久許可がない場合は安全な個別承認を案内し、承認UIの迂回・無断拡大をしない。
- **引継ぎと検査**：既存KB・BUILD_PLAN等を正本とし、依頼→実行→結果の原則1往復で、ID・担当・証拠・次の行動・中継上限を簡潔に残す。チャット作成成功・再読込・プラグイン実許可・定期実行を別々に`PASS / FAIL / NOT_RUN / N/A（理由）`で記録し、未確認は自動化済みと呼ばない。

**AIへの追加指示**：初期導入後、上記を強制せず、利用者に最小1案と未対応部分の手動代替を提示する。無断の新規チャット作成、定期ジョブ登録、権限変更、削除、外部共有はしない。
