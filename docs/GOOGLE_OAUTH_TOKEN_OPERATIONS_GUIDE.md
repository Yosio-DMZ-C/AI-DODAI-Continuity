## 0. 全体マップ｜費用と手間のカベを先に知る

| 工程 | 何をする？ | お金のカベ | 手間・時間のカベ | 必要な人 |
| --- | --- | --- | --- | --- |
| ① 現状確認 | Google Cloudで対象プロジェクト、OAuthの公開状態、使う権限（スコープ）を確認 | 通常0円 | ログインと画面確認、約5〜15分 | 全員 |
| ② 方針選択 | A「本番化」、B「本番化＋Google確認」、C「テストのまま7日再同意」から選択 | 0円 | 数分 | 全員 |
| ③ 本番公開へ切替（A/B） | Google Auth Platformの「対象ユーザー（Audience）」で公開状態を切替 | 切替操作の定額料金なし | 約5〜15分。Google側の警告・要件を確認 | A/B |
| ④ 接続を読取検査（A/B） | 旧トークンが有効か確認し、失効時だけ安全な経路で再同意 | 通常0円 | 約5〜15分。再同意が必要な場合あり | A/B |
| ⑤ 自分のドメイン（B） | アプリの公開サイト・プライバシーポリシーを自分のドメインに設置し、所有確認 | **既所有：追加0円のことが多い／新規：約1,000円/年は目安**（更新料は別途確認） | DNS・サイト設定に数十分〜数時間。反映待ちあり | B |
| ⑥ Googleの確認申請（B） | アプリ情報、利用目的、必要な権限、動作説明動画等を提出 | Google申請自体に一般の定額申請料は確認されない。**制限付き権限は第三者セキュリティ審査等の費用が発生し得る** | 目安：ブランド2〜3営業日、機密性の高い権限約10営業日、制限付き約6週間。差戻しで延長 | B |
| ⑦ 7日ごとの再同意（C） | 失効を検知→Google同意→更新トークンの安全な再登録→読取検査 | 通常0円 | **約7日ごとに本人の操作**。省略不可 | C |

**課金の読み方**：OAuthを「本番」にすることと独自ドメインを買うことは別です。既存ドメインなら新しい購入は不要です。ドメインの約1,000円/年は低価格帯の参考値で、初年度キャンペーン、翌年更新、DNS・ホスティング、税、為替で増減します。Cloudflare・Google Cloud・各APIは、選んだプランや利用量によって別途費用・無料枠・クォータがあり得ます。購入・有料プラン・課金有効化は金額を見て本人が決定してください。

**時間の読み方**：上記は計画用の目安であって所要時間の保証ではありません。Google公式の審査期間は目安で、差戻しや追加書類により延びます。

### どこまで必要？ 30秒で判断

- **A：自分専用で7日失効を避けたい** → **「本番化」から始める**。未確認アプリ警告や未承認スコープのユーザー数上限は残り得ます。自分で使うだけなら、それで実用になる場合があります。ただしGoogleのルール・スコープによる例外や制約は確認してください。
- **B：知人・不特定多数にも安心して利用してほしい** → **「本番化」＋必要なGoogleの確認**。承認された権限について警告や未確認アプリのユーザー数上限が解消します。Google Workspace管理者による別のブロック権限まで解除されるわけではありません。
- **C：一度設定したら長期放置する必要がない／審査の手間をかけたくない** → **テストのまま約7日ごとの再同意**。これも正規の選択肢です。期限のたびに実際の人間操作が必要です。

**混同しない**：「公開状態＝本番（In production）」は「Google確認済み（Verified）」ではありません。「確認済み」はGoogle Workspace管理画面の管理者設定「Trusted」とも異なります。テスト状態の7日失効は、外部向けでプロフィール以外の権限を要求する場合の原則です。Googleアカウントの一般的な短命アクセストークン（通常約1時間）とは別の話です。

## 1. 共通の準備：現在のアプリを確認する

1. [Google Cloud Console](https://console.cloud.google.com/)へログインし、**画面上部で対象プロジェクトを選ぶ**。別のプロジェクトを編集しない。
2. [Google Auth Platform](https://console.cloud.google.com/auth/overview)を開き、左メニューの **対象ユーザー（Audience）**で「外部」「テスト（Testing）／本番（In production）」を確認する。直リンクが開かないときは画面のメニューから移動する。
3. **データアクセス（Data Access）**で要求済みスコープと「機密性が高い（Sensitive）／制限付き（Restricted）」等の区分を確認する。必要以上に広いスコープを追加しない。[データアクセスの公式入口](https://console.cloud.google.com/auth/scopes)
4. **クライアント（Clients）**では現在使うOAuthクライアントの種類と、Worker・アプリ側の設定が対応していることだけ確かめる。すでに動くクライアントを根拠なく作り直さない。**client_secret、アクセストークン、更新トークン、パスワード、アクセスキーは画面共有・GitHub・通常のチャットに記載しない**。値の所在は非公開の「鍵メモ」を参照する。
5. 既存の接続が動く場合、先に**投稿・変更を伴わない読取API**で確認する。接続未確認のまま動画投稿・公開は実施しない。

## 2. A/B共通｜OAuth同意画面を「本番」にする

1. 上で確認した同じプロジェクトの **Google Auth Platform → 対象ユーザー（Audience）**を開く。[公式画面](https://console.cloud.google.com/auth/audience)
2. 対象ユーザーが「外部」で、公開ステータスが「テスト」の場合、**アプリを公開（Publish app）**を選ぶ。確認ダイアログの内容を読み、必要な案内があれば従う。社内専用の「内部（Internal）」アプリは同じ手順をそのまま当てはめない。
3. 画面を更新し、**In production**になったことを読み戻す。ここで作業を止めてもよい（コースA）。
4. 既存の更新トークンが有効ならそのまま読取テスト。**既に失効したトークンは本番化だけでは復活しない**ので、後述の再同意手順で更新してからテストする。以後も利用者による取り消し、長期未使用、トークン上限、Google側の方針等で失効することはあります。
5. 未確認アプリの警告が出ても、**本番切替が失敗した証拠ではありません**。公開ステータスと確認ステータスを別々に見る。警告の解消が必要なら次のコースBへ進みます。

**確認結果**：本番ステータス表示／読取API成功の2件を別々に確認。7日以上の継続動作そのものは、継続期間が経過するまでは未検証です。

## 3. Bのみ｜Google確認の準備・申請

### 3-1. ドメインのカベ

**現実解は「すでに所有するドメインを使う」か「安価な独自ドメインを1つ取得する」**です。無料ドメイン探しは、安定性・更新継続・所有確認の面で時間を浪費しやすいため標準経路にしません。

- GitHub Pagesの github.io や Cloudflareの workers.dev のような**公開サフィックス配下の共用URL**は、URLとして利用できても、Google OAuthの **承認済みドメイン（Authorized domains）として本人所有の登録可能ドメインと認められるとは限りません**。OAuthのリダイレクト先URLとしての可否と、審査用ドメインの所有確認は別判定です。
- 既存サイトのある人は、そこに**アプリ概要ページ**と**プライバシーポリシーページ**をHTTPSで公開するのが最短です。内容・URLは実在するものを使います。ポリシー本文はこのガイドでは作りません。
- Google Search Consoleでは、**Google Cloudプロジェクトのオーナー／編集者と所有確認済みアカウントの関係**を合わせて確認してください。審査でドメイン所有が認識されない場合は、**ドメインプロパティ（DNS TXT等）**による確認を優先します。URLプレフィックス登録があるだけで審査に通るとは断定しません。
- **適用例：既所有の campsite7.jp を第一候補**。Search Console登録済みという前提でも、当該GCPプロジェクトと同じ管理者に所有権が見えるか、Domain propertyになっているかはGoogle画面で改めて確認します。新規ドメイン購入はその結果を見てから。

### 3-2. ホームページとプライバシーポリシーの配置

1. 所有確認済みの独自ドメイン上に、誰でも開ける**アプリ名・目的・主機能・問い合わせ先**を示す公開ページを用意する。ログイン画面だけのページにはしない。
2. 同じサイト配下に、Googleデータの取得・利用・保管・共有・削除や問い合わせ方法を説明する**公開プライバシーポリシーのURL**を用意する。トップページからリンクを張る。**文案は個人KB側で別途準備中**のため、このガイドには本文例を収録しません。
3. Google Auth Platform → **ブランディング（Branding）**でホームページURL、プライバシーポリシーURL、承認済みドメイン、サポート窓口等を実サイトと一致させる。OAuthクライアントのリダイレクトURI・JavaScript生成元もアプリの実装と一致させる。**認証フローのURLを確認なく変更しない**。

### 3-3. Googleへ確認を申請する

1. Google Auth Platformの **確認センター（Verification Center）／画面上の「確認に送信」**から必要な種類を確認する。スコープ区分・公開先により要求内容は変わります。
2. アプリの説明、要求権限を使う正当な理由（最小スコープ）、実際に使うページ、連絡先を提出する。Sensitive/Restrictedでは**OAuth同意から機能利用までを示すデモ動画**等が必要になり得ます。動画に秘密値や個人データを映さない。
3. 申請後はGoogleからのメールや画面にある要求事項に応じ、**審査結果の確定を待つ**。差戻し時は指摘項目だけ直して再提出。新しい権限を追加すると再確認が必要になる場合があります。
4. 承認後、対象スコープの警告・上限が解消しているか確認し、別の許可済みアカウントで読取テストする。**確認申請を送っただけで確認済みとは扱いません**。

## 4. C｜「本番化はいらない」人の7日再同意運用

継続的な審査・ドメイン費用を避けたい場合は、**テスト運用＋再同意**を選んで構いません。ただし、外部／Testingの更新トークンは対象スコープで通常7日で失効します。翌週も自動で使えるという運用にはしません。

1. **失効検知**：Worker／道具の読取チェックでOAuthエラーを確認。よくある例は invalid_grant、再認証を求める応答。ネットワーク障害・スコープ不足・クォータ超過と区別する。投稿エラーを見て自動再投稿しない。
2. **再同意ページ**：その道具に組み込まれた**正規のOAuth開始ページ**、または既存の認証セットアップツールから開始する。ネット検索で見つけた見知らぬ同意ページや、AIが推測で作ったURLを使わない。実際に登録したOAuthクライアントとリダイレクト先を使う。Googleにログインし、対象アカウント・権限・YouTubeの場合は対象チャンネルを確認して本人が同意する。
3. **トークンの受渡し**：認証ツールが更新トークンをコピー用に表示する方式なら、**文字列としてコピーして、指定された安全なSecret入力欄へ直接渡す**。**スクリーンショットからの転記・OCR・手打ちは禁止**（文字欠け・誤入力を招く）。ツールがトークンを画面に出さずCloudflare Secretへ安全に直接保存する方式なら、それを優先する。**通常のAIチャット、GitHub、メール、共有ドキュメント、スクリーンショットにトークンを貼らない**。
4. **保存後の確認**：WorkerのSecretが更新されたことを**値を表示せずに**確認し、読取のみのチェックと対象アカウント照合を実施。失敗時は認証・Secret名・対象プロジェクト・スコープを点検し、むやみに再同意を繰り返さない。
5. **次回**：約7日後に同じループ。本人の手作業が発生する前提で予定を組みます。「鍵メモ」には値の在処と手順を記し、**秘密値そのものはこの公開ガイドに書かない**。

**注意**：新しい更新トークンを繰り返し発行すると、アカウント／クライアント単位の発行上限等で古いトークンが無効になることがあります。更新前に実際の接続失効を確認してください。

## 5. YouTube Posterへの適用例（一般手順との違いだけ）

対象：Cloudflare Worker **adnc-youtube-poster** → Google OAuth更新トークン → YouTube Data API。**本番WorkerのSecret値、設定済みGoogleプロジェクトID、クライアント情報はここに記載しません**。所在は非公開の「鍵メモ」で確認してください。

| 段階 | 人間が確認する操作・成功条件 |
| --- | --- |
| 入口 | Google CloudのYouTube Poster用プロジェクトを選び、**AudienceのTesting／In production**を確認 |
| 推奨 | 自分の継続運用ならまず**コースAの本番化**。Google確認の要否は後から判断。長期運用を優先 |
| 本人用ドメイン | 申請が必要なら **campsite7.jp** を第一候補として、Domain propertyとGCP権限を照合。プライバシーポリシーは個人KBで用意された完成版を所定ページに設置 |
| 秘密情報 | Cloudflare Dashboard → **Workers & Pages → adnc-youtube-poster → Settings → Variables and Secrets（画面表記に従う）**。秘密値はSecretとして登録・更新し、平文Variablesへ保存しない。**Secret名・OAuth経路は既存実装／鍵メモで確認し、推測で新設しない** |
| 接続検査 | YouTube Posterの **get_channel_info（読取専用）**等、現行アプリが実装した接続確認を実施。意図したチャンネルか確認。読み取りPASSと実動画投稿PASSは別 |
| テスト継続 | コースCを選んだ人のみ、失効検知→既存の正規同意ページ→**テキストコピーで安全なSecret受渡し**→get_channel_infoで再確認 |

**YouTube特有の注意**：Googleアカウントとブランドアカウント／チャンネルの選択は同じとは限りません。実際のAPI接続先を読取結果で照合します。OAuthの保守作業のために動画を新規投稿・公開しないでください。

**関連の設計参考**：既存[YouTube関連Draft PR #21](https://github.com/Yosio-DMZ-C/AI-DODAI-Continuity/pull/21)には別世代の初回認証手順やWorker試作があり、現行Workerの設定値・実装状態を保証する正本ではありません。**今回の一般ガイドで古いWorkerへ置き換えない**でください。

## 6. 詰まったときの最短復旧

| 現象 | 最初に確認すること |
| --- | --- |
| 7日前後で止まる | AudienceがExternal/Testingか、更新トークン失効かを切り分ける。本番化するかコースCへ |
| invalid_grant | 期限切れ、同意取り消し、クライアント変更など。対象を確認し、必要なときだけ正規経路で再同意 |
| redirect_uri_mismatch | OAuthクライアントの登録済みリダイレクトURIと実際のリクエストが完全一致しているか |
| 「未確認アプリ」警告 | 公開ステータスとGoogle確認のステータスを分けて見る。警告解消が目的ならコースB |
| ユーザー数上限 | 未承認のSensitive/Restrictedスコープがないか、Google確認ステータスと上限利用状況を確認 |
| ドメインの所有が認識されない | Search ConsoleのDomain property、GCPのOwner/Editorと所有確認アカウント、DNS TXTを確認 |
| YouTubeの違うチャンネルにつながる | 同意に使ったGoogleアカウント、ブランドチャンネル選択、get_channel_infoの実応答を確認 |
| 403／quota／権限不足 | API有効化、必要スコープ、利用枠・ポリシーを確認。**トークン再発行だけで直るとは限らない** |
