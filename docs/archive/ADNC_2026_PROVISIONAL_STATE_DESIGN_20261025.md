# AD&C｜2026年の暫定アーキテクチャ決定：状態整合性・更新・復旧

- 状態：**暫定採用／β設計指針**（2026-10-25）。本書自体は配布版・個人KBの変更指示ではない
- WHY：2026年10月のGrok／Muse A／Muse Bの設計監査と、Muse A・AD&C調査担当・GrokによるOS先行技術研究、PR担当の一般標準／案件固有条件の報告を統合する
- 位置：**既存Issue #13の意思決定資料**。新しい管理制度・台帳・常駐ジョブは設けない
- 保全範囲：**公開しても差し支えない研究内容と採否理由**。私的なKB本文・個人情報・DriveファイルIDは転載しない。各報告の原文は依頼時のチャットにある。本書は引用と再構成による詳細要約であり、原文全文の逐語複製ではない
- 見直し条件：架空KB故障注入、別AI実行、実KBでの偽陽性・偽陰性、Driveの書込条件APIの実証結果が出たときに**この決定だけ**見直す

## 暫定結論（2026年）

AD&CをOSや分散DBへ作り替えない。「**固定した識別子と採用判断は守り、再計算可能な派生値だけ検証し、小さい差分を再確認してから採用し、結果を別AIが実体から読み直せる**」方式を採用する。

- **正本として保護**：NodeID、レコードID、Drive fileId、採用された論理パス、承認履歴、変更前スナップショット、採用済み制作方式などの**人間が決めた条件**、実際の確認・更新という出来事の日時。**これらは現在の本文から全て再生成できるわけではない**
- **導出・検査対象**：実際の本文から計算できるSHA-256、サイズ、取得済み集合の件数。索引・カタログの生成は**失われる情報がないと確認できた部分だけ**。既存の手作業で付いた判断・注記を勝手に消さない
- **状態の分離**：内容同一性（ハッシュ）、採用版／現行性、複数文書の集合整合、意味的正しさ、実行・受渡し成功、外部作用の取消可能性を**異なるゲート**として報告
- **競合**：対象ファイルを取得した時点の基準値と、書込直前の実値を比べ、不一致時は対象だけ停止／差分マージ候補化。ただしDriveでサーバー側の条件付き更新が確認されるまで、チェック直後から書込までの競合（TOCTOU）を**排除できない**。複数AIの同一KB確定書込は当面1担当に集約し、他担当は読取・提案・隔離試験に限定
- **利用者負担**：小さく可逆・対象と権限が**承認済み**の作業は既存のcontinuous方針に従い連続実施。未承認の個人KB編集・公開・送信・課金・削除・権限変更を「低リスク」を理由に無断許可しない
- **採用条件の優先順位**：今回の明示指示 → 取得・確認した案件固有の採用条件 → 該当箇所の一般標準 → 未決定部分に限るAIの可逆的裁量。単に「昔使った」だけの履歴は、現在の採用・課金承認とみなさない

## 2026年の更新契約（β・非原子的な環境）

1. **取得**：START_HERE／BUILD_PLAN／registryの必要部分と対象ファイルを実取得。正しいKB、対象ID、実際の今回の承認、現在の採用状態、既存の課題・前例を同定。取得不能ならNOT_RUNとし「不存在」と混同しない。
2. **基準保存**：対象の現在ファイルID・ハッシュ・改訂番号・作業単位の現行再開位置を、既存のBUILD_PLAN／当該作業契約に保持。対象の変更前実体は既存履歴へ保全。**その時点で競合しないことだけでは将来の競合排除を保証しない**。
3. **候補を作成**：メモリや古い散文を前提にした全量置換を避け、小さい差分候補を作る。新IDの候補ファイルを本番の「採用済み正本」と偽らない。原本のfileId維持が必要なら切替方式ではなく安全な同一ID差分更新を優先。
4. **変更前照合**：現行実体を再取得し、基準と差分を比較。基準≠現行は無断上書きしない。独立なレコード／節の変更で安全に統合できると判断する場合も、参照・意味・承認・同時編集の影響範囲を確認。**単なるハッシュの三方比較だけで自動マージ安全性は保証しない**。
5. **保存と検収**：許可範囲内で対象のみ更新。対象の実読戻し・実バイトSHA・registryとの一致・BUILD_PLANの現行再開位置を検査。関連文書が複数なら、**全て一致するまで「更新完了」としない**。途中成功・失敗・NOT_RUNを別々に記録する。
6. **回復**：他者の変更や未確定作業を上書きしない。旧版へ戻す操作も**新たな変更**であり、現行状態の取得・承認・復旧範囲の確認を経る。送信・課金・公開済みの事実はregistryを戻しても消せない。

この契約は、Drive上での**実際の原子的トランザクションを保証しない**。同時更新・中断時にどう読まれるかは隔離実験で検証する。Gitのcompare-and-swapやGCSの世代条件と同等と主張しない。

## 何を同時に保証したと誤解しないか

| 観点 | 正本・検査 | PASSから保証しない範囲 |
|---|---|---|
| バイトの同一性 | 取得済み原本とSHA-256／サイズ | 現行採用版、意味の正しさ |
| 登録関係 | registryの固定ID・fileId・パス／レコードとの一致 | Driveでのサーバー側競合排除 |
| 更新の採用 | BUILD_PLAN上の採用判断・実読戻し・旧版保全 | すべてのAIが既に新版を認識したこと |
| 再開の一意性 | 案件ごとの現行再開位置と履歴の分離 | 複数案件の全KB共通「最後の一行」化 |
| 機能の稼働 | 秘書・日記・運用タスクなどの個別実行証拠 | インストーラー版の数字だけでの機能実装 |
| 利用者の成果 | 必要成果物の存在・実再生／受領・検収 | ファイル名やQA文書に「完成」と書いてあるだけ |

## 検査の設計・配備判断

- **変更直後の安い検査**：変更した対象の取得成功（種類・サイズ・内容）、実ハッシュ、対応する台帳レコード、必要な参照・構文・再開位置。**取得失敗とハッシュ不一致を別判定にする**
- **必要に応じた全体検査**：全件参照切れ、重複、未追跡ファイル、索引／registryの陳腐化、世代候補の確認。既存の月次運用に載せるのは実際に稼働する環境と承認がある場合のみ。未設定のジョブをあるものと扱わない
- **実装単位**：新たなチェック器群ではなく、既存の[PR #32](https://github.com/Yosio-DMZ-C/AI-DODAI-Continuity/pull/32)の読取専用プローブを新旧registry形状（`revision`と`meta.revision`）へ適合させ、まず合成KBで検証。作業単位の採用条件・素材復元は既存の[PR #31](https://github.com/Yosio-DMZ-C/AI-DODAI-Continuity/pull/31)の検証対象を再利用可能か評価。2つを無条件マージ・二重開発しない
- **再開状態**：歴史の見出しを複数見つけただけで自動FAILとしない。案件固有の**現行**再開位置を、過去の追記履歴から別に識別できることが重要。マーカー追加だけで意味的矛盾がなくなったと主張しない
- **派生索引の生成**：現行索引1件とregistryによる仮生成物の差分を、(a)台帳が新しい (b)索引独自の人間注記 (c)生成器欠落、の3種類に分類する**読み取り専用試験から**。差分に固有情報があれば本採用保留
- **資料到達と一般標準**：Runbookは最初に当該案件の採用条件・必要な素材・既知の問題を取得し、一般標準を未決定事項に適用する。すべての手順で「前例ID必須」にはしない。後から見つけた素材が以前の課金・公開を許すわけではない

## 先行技術の研究素材（4担当の見解、違いを保持）

### Muse A：旧KBの現場観測・OS対応
- Nix／OSTreeから「旧版保全→検査→採用」の考え方。ZFSから「対象の読取り時は安い検査、全体はscrub」の分離。SQLiteから状態の実体保存。dpkgから利用者改変の保全・必要時だけ競合確認。
- 実観測：141件の台帳を確認したが全141ファイル本文を実測していない。**サンプル8件のハッシュを正しく再取得して再照合した結果、6件一致、2件不一致（派生系）**と報告。最初は取得方法の誤りで「全件不一致」という**偽アラーム**があり訂正された。これを全件の整合率として外挿しない。
- 提案の強い点：索引1件の**仮生成・差分分類**。生成器に必要な情報がregistryに存在するかを先に判断できる。
- 注意：`last_checked_at`は現在の実体から再計算できる派生値ではなく、**検査した時刻という出来事の記録**。履歴と承認の情報を再生成・消去してはいけない。
- 注意：ファイル内容を先に書込み、後で参照を切替える設計は、同一fileId契約や非原子的Drive更新にそのまま移植できない。

### AD&C調査担当：技術原則・破壊的でない故障注入
- NixOS/OSTree：世代・候補・確定の分離、旧版復旧の限界
- OpenZFS：整合性・参照ツリー、冗長コピーなしではscrubは修復を保証しない
- SQLite：journal/WAL、コミット前後の境界、I/O失敗・クラッシュ試験、単独書込みの考え方
- Debian：利用者の設定保全と再実行・冪等な処理
- **Google Drive API v3**：`version`、binary限定の`headRevisionId`、対応ファイル限定の`sha256Checksum`等はある。ただしfiles.updateで期待版と一致した場合のみサーバー側で確定する契約は本調査で未確認。取得→照合→更新の間に別操作が入るTOCTOUを現行手順だけでは排除できない。
- 提案の強い点：同じrevisionからの**二者更新＋候補保存後の中断試験**。単なる設計レビューでなく、競合・復旧を独立判定する。
- 不採用：WALをDriveフォルダへ流用／真のatomicityを宣言／全OSスタックを複製。

### Grok：世代ドリフト・偽の安全感への警告
- 最も重要な盲点を「AIが読んだ版と書く時点の版の時間的／意味的乖離」と整理。
- 提案：`START_HERE`・`BUILD_PLAN`・対象registryの**基準状態**を示す世代チェックポイントを使って書込直前に照合し、乖離を検知する。PR #31/#32の境界を維持する。
- 注意：ファイル内に基準メタデータを追記するだけでは同時書込を**サーバー側で拒否するCASにならない**。本当に書込直前の照合が実行されるか、照合後の競合を防げるかは別問題。新しいメタ欄は先に必須化せず、実験と比較する。
- 提案の強い点：正当な正常更新と、別AIによる世代変更があった場合を**同じ検査器の合成ケース**で比較する。Driveの本番ファイルには触れない。

### PR責任者：一般標準と案件固有の確定条件
- 同じ「第2作を制作して」という指示から、あるAIは一般標準の本人朗読を提示し、別AIは旧採用音源の復元を考え質問した。**両者の動作差は観測**だが、旧案件固有条件の取得可能性と実取得ログは未確認で、いずれかが無条件に誤りとは断定しない。
- 合意候補：**現在の本人指示 → 現行案件で採用済みと実取得できた条件 → 一般標準 → 未決定部分のAI裁量**。以前使った方法や資産があるだけで、方式採用・新しい課金や権限が承認されたことにはならない。
- 対象は動画に限定しない。既存案件の再開、文書再編集、コード修正にも同じ順序が必要。
- 安全ゲート（公開／送信／課金／削除／ACLなど）はこれらの優先順位で解除しない。

## 2026年に見送る提案・理由

| 提案 | 判定理由 |
|---|---|
| registry全体をファイル群から自動再生成 | 固定ID・fileId・人間の判断・履歴などを再生成できない |
| 全ファイルをNixストア型の新IDへ置換 | 既存Drive fileIdの維持契約と衝突 |
| Drive上にSQLite WAL／疑似分散ロック | 排他・失敗回復の前提がなく複雑化する |
| 「取得直前確認」で競合排除を保証 | 照合直後と更新直前の競合窓が残る |
| 全ての低リスク修正を無断で自動確定 | 利用者の承認範囲と、可逆性の判断が必要 |
| 長大なインストーラーを一気に3層に物理分割 | 既存の入口・旧KBとの互換・更新導線を壊す可能性 |
| 版不明の旧KBへ設計版からinstaller版を推測して付与 | 版の意味が異なり、証拠なくFROMが確定したことになる |
| BUILD_PLANを全案件共通の最後の1行へ固定 | 並列するProjectsの正しい現在状態を消してしまう |
| 既存秘書の日次確認だけで全KB常時監視を保証 | 実行される保証がなく、未接続環境もある |

## 試験設計（架空データのみ・実環境と分けて判定）

| 試験 | 故障注入／観測条件 | PASS条件 | 既知の未実装 |
|---|---|---|---|
| A 検査器の正常／異常 | flat revision、nested `meta.revision`、SHA不一致、取得失敗 | 本文と台帳の実不一致をFAIL、取得不能をNOT_RUN | PR #32の旧KB適合とCIの再検証 |
| B 中断・競合 | 基準A=基準B、Aが書込後停止、Bが古い版から保存を試みる | 期待状態の変化を検知・無断上書きせず保留。**Driveの原子的排他PASSとは別** | 実Drive競合注入NOT_RUN |
| C 索引仮生成 | 既存索引1件とregistryの仮生成物を比較 | 全差分が分類され、索引固有注記を失わない | 実索引の差分分類NOT_RUN |
| D 再開意味検査 | 同一案件の現行再開位置2候補、過去履歴に多数の見出し | 歴史の重複による偽FAILを防ぎ、現行矛盾を検出またはNOT_RUNにする | AIによる意味判定NOT_RUN |
| E 案件標準優先順位 | 新規／案件固有方式採用／音源のみ有／取得不能の4例 | 採用条件を実取得して継承、未決定部分だけ一般標準 | 別AI独立試験NOT_RUN |

**試験の順番**：A（検査器の健全性）→B（非原子的更新の失敗限界）→C（索引生成可否）→D/E（意味・運用検査）。実データの自動書込や配布版更新は**評価後**。
